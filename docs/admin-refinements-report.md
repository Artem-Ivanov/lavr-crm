# Исправления входа и обращений

Дата: 02.11.2026. Функциональность реализована и проверена локально; production не обновлялся.

Выполнены семь требований:

- Одна форма email/пароль для кабинета и всех служебных ссылок, включая карточки из Telegram. Исходный маршрут сохраняется при входе, регистрации и восстановлении.
- Email стал единственным идентификатором входа. Совместимое поле API `login` содержит тот же email; отдельный прежний логин в списке пользователей скрыт. Проверка подтверждения, блокировки, общие лимиты попыток, CSRF и разграничение прав сохранены.
- Оба типа обращений используют общую PostgreSQL-последовательность и целочисленный номер. Отображение: `№12 от 02-11-2026 13:45`, московское время. Миграция `0006` перенумеровывает канонические старые записи по времени создания и UUID.
- Кнопки входа и выхода используют одинаковые стили и размеры; скругление и цвет дополнительно сравнены настоящим браузером.
- В списке обращений фиксированы колонки номера и статуса, текстовая колонка занимает оставшееся место. На мобильном строки складываются в карточки. Статусы и описания Telegram показываются по-русски; диагностические коды доступны вторично.
- Удалена кнопка «Проверить сессию».
- Полностью удалён блок «Подготовлено к интеграции с 1С» и его неиспользуемые стили.

UUID, ссылки, владельцы, пароли, роли и действующие сессии сохраняются. Ранее выданные публичные квитанции, зашифрованные ответы конвертации и relay/outbox snapshots не переписываются, поэтому в исторической квитанции может остаться прежний строковый номер. Уже отправленные Telegram-сообщения не менялись. Sequence может пропускать значения при rollback; это не счётчик без пропусков.

Работу выполнили три сабагента с раздельным владением файлами, каждый участок проверил независимый ревьюер. Root проверил интеграцию в отдельной рабочей копии с сохранением текущих незакоммиченных изменений проекта. Ревью выявило и помогло исправить конфликт старого login-индекса при создании нового сотрудника; браузер выявил и помог исправить разное скругление/цвет входа и выхода.

Проверки:

- Полный backend: **420 passed**, включая реальную PostgreSQL-миграцию, конкурентную нумерацию, идемпотентные повторы и сохранение зашифрованных снимков.
- Frontend: **181 passed**, синтаксическая проверка и production/demo build прошли.
- Пять браузерных наборов: **72 passed** после обновления устаревших сценариев входа; дополнительно два регрессионных сравнения стилей прошли на desktop/mobile.
- Отдельная проверка реального backend + Chrome: числовые обращения `1, 2, 3`, возврат к карточке и reload после email-входа, admin `login=email`, отказ partner в служебном доступе, собственное обращение, одинаковые стили кнопок, отсутствие удалённых блоков, ширины 1440/390/320 px. Ошибок JavaScript нет. Использовалась отдельная база `lavr_admin_refinements_test`; Telegram/SMTP выключены.
- OpenAPI YAML проверен, контракты числовых номеров и email согласованы. Скриншоты и отчёты находятся в `.planning/2026-11-02-admin-refinements/`.

Дополнительный полный демо-smoke прошёл **20/20**. Пять сценариев, рассчитывавших на автоматический вход администратора в демо, обновлены явным email-входом; проверки заказов, мобильных контролов и экранирования текста сохранены.

Итоговое независимое ревью выявило одно существенное замечание: клиент отклонял адреса с `#`/`?`, которые сервер уже поддерживал. Исправлен общий клиентский предикат email без изменения существующих пользователей; две регрессии сначала воспроизвели ошибку, затем прошли. Полный frontend повторно прошёл 181 тест. Дополнительная проверка настоящим backend/Chrome создала таких операторов штатной командой provisioning, подтвердила нативную валидность email, загрузку административного списка и вход обоих операторов с возвратом в ту же карточку. Ошибок JavaScript нет. Остальных существенных замечаний итоговое ревью не выявило.

Локальные стенды оставлены для просмотра: реальный тестовый API/frontend — http://127.0.0.1:5186, демо — http://127.0.0.1:5189. В демо доступны `admin@example.test`, `operator@example.test`, `partner@example.test` с любым непустым паролем. Реальный локальный стенд использует только синтетическую базу и отдельные закрытые настройки в `.planning/2026-11-02-admin-refinements/private/local.env.json`.

Перед будущим production-обновлением нужно проверить подтверждённый email у сотрудников, включая активного администратора, и применить миграцию в окно обслуживания. Старым учётным записям без email адреса автоматически не назначаются. Для новой установки генератор оставляет `ADMIN_LOGIN` пустым: оператор заполняет реальный email перед первым запуском; существующий env и существующие пользователи не перезаписываются. Пароль CLI вводится скрыто. При downgrade числовые номера сохраняются строками; исходные канонические метки без backup не восстанавливаются.
