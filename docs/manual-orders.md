# Заказы в CRM без 1С

Покупатель добавляет товары в корзину и оформляет самовывоз без онлайн-предоплаты;
оплата производится в магазине. Форма содержит контакты, адрес/часы магазина
из настроек и кнопку «Заказать с самовывозом». Доставки и адреса покупателя нет.
Новые гостевые и кабинетные delivery-запросы отклоняются сервером, а история
и повторы ранее сохраненных заказов не меняются. Второй сценарий с оплатой через
банк описан в [checkout-flows.md](checkout-flows.md) и пока не реализуется.
Сервер проверяет цену, единицы, остаток и свежесть каталога. Заказ получает
статус «Новый», `integrationStatus: not_connected` и локальный резерв.
Событие `order_telegram` сохраняется в той же транзакции. Повтор запроса
с исходным ключом возвращает прежнюю квитанцию без второго заказа или резерва.

Менеджер проводит заказ через «Подтвержден», «Готов к выдаче», «Завершен».
Отмена разрешена до завершения и освобождает резерв. Завершение одновременно
уменьшает физический остаток и резерв; доступность от этого не увеличивается.
Все изменения используют текущий `If-Match`, блокировки строк и аудит.
Доставленные или уже отправляемые Telegram-события отмена не переписывает.

Если адаптер 1С настроен при создании, сохраняется прежний путь
`pending_sync` / `order_export`. Режим уже созданного ручного заказа не меняется
после подключения адаптера; старые ручные заказы автоматически не экспортируются.
Новая миграция БД не требуется: используется схема 0009 и существующие статусы.

## Telegram

Используется существующий relay с постоянной квитанцией и повторными проверками.
Сообщение содержит номер, время по Москве, сумму и число позиций. Кнопка
«Открыть заказ» ведет в защищенную CRM. Контакты и адрес покупателя в канал
не передаются. Прием relay в очередь не считается доставкой: нужен положительный
Telegram message ID для того же события и notification receipt.

Для обработки только новых заказов запустить существующий сервис `notifications`
с командой `python -m app.notification_worker --orders-only` и
`TELEGRAM_NOTIFICATIONS_ENABLED=true` в окружении этого worker. Relay-настройки,
ключи шифрования и CA должны совпадать с API. Режим не обрабатывает старые
`feedback_telegram`, письма и ERP-задания. Настройки API можно оставить с false.

Перед первой активацией проверить очередь, установить новую проверенную версию
`ops/deploy.py` вне Git checkout и обновить private deployment state с фактическим
`images.notifications`, хешами защищенных Compose-настроек и прежним `data_verified`.
Worker должен использовать тот же backend image и точную команду с orders-only.
Git-деплой затем обновляет API и активный worker вместе. После приема ручных
заказов использовать только совместимые версии; старый `256f160` несовместим.
Новый controller проверяет нужные возможности кандидата до maintenance.

## Остатки

Свежесть каталога по-прежнему ограничена 24 часами. Загрузка следующего файла
назначает абсолютные остатки: файл должен учитывать ручные продажи и отражать
актуальный склад. Завершение заказа не подменяет дату внешней инвентаризации.

Проверки выполняются на изолированной тестовой PostgreSQL: конкурентный последний
остаток, повторы, дробные кг, откаты при ошибках БД, переходы менеджера и защита ERP.
Настоящая доставка на production проверяется после Git-деплоя отдельным явно
тестовым заказом с последующей отменой и освобождением его резерва.
