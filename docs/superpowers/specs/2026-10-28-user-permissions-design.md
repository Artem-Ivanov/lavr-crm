# Пользователи и права MIRZAP67

Дата: 28.10.2026. Статус: дополнение к проекту аккаунтов; реализация не начата. Пользователь подтвердил, что admin автоматически имеет полный доступ. Этот документ заменяет прежнее предположение о раздельных паролях покупателей и сотрудников.

## Требования пользователя

- Нужна административная страница пользователей и прав.
- Администратор редактирует сайт и назначает права пользователям.
- Общие заказы, служебные настройки и сведения самой системы доступны operator и admin; admin автоматически имеет полный доступ.
- Новый зарегистрированный пользователь по умолчанию получает partner.
- Названия/статус прав пользователя видит только администратор.
- Сохраняются ранее согласованные гостевые заказы без владельца и ЛК с собственными заказами/обращениями после входа.

## Подтверждённая матрица доступа

Используем одну роль partner, operator или admin. Partner — базовый доступ активированного аккаунта; operator добавляет операционные возможности, admin включает все возможности operator, редактор сайта и управление пользователями. Одновременно назначать две роли не требуется.

| Возможность | Partner | Operator | Admin |
| --- | --- | --- | --- |
| Собственные заказы/обращения и создание от своего имени | Да | Да | Да |
| Общие заказы, обращения, заметки и рабочие статусы | Нет | Да | Да |
| 1С, диагностика доставки, служебные настройки | Нет | Да | Да |
| Контент, медиа, публичные настройки и оформление каталога | Нет | Нет | Да |
| Список пользователей, просмотр/назначение их прав | Нет | Нет | Да |

Собственный список заказов в ЛК и общая операционная страница — разные проекции с разными проверками доступа. Partner не теряет собственную историю из-за operator-ограничения общей CRM. Публичные каталог и страницы доступны гостям.

«Публичные настройки сайта» — название, контакты, часы работы, заголовки, оформление; это редактор сайта для admin. «Служебные настройки» — интеграции, состояние очередей и доставки; это operator и admin. Пароли, OTP, ключи шифрования, токены ботов и SMTP не возвращаются браузеру при любых правах.

## Одна учётная запись

- Одна User identity хранит пароль, активность, зашифрованный профиль, email lookup и подтверждение, auth_version и поле role с допустимыми partner/operator/admin. Новая регистрация всегда устанавливает partner на сервере.
- Таблица произвольных ролей, конструктор разрешений и отдельная Staff identity не нужны для трёх заданных ролей.
- Назначение operator/admin меняет эту же запись, а не создаёт сотрудника с другим паролем. Владение ранее созданными заказами/обращениями сохраняется по User.id.
- Один UserSession и существующее техническое имя cookie lavr_session. Новые пользователи входят по подтверждённому email и паролю. Совместимый вход по старому staff login обращается к той же User и тому же паролю.
- Публичные signup/profile/order input-модели запрещают role, capabilities, is_active, verifiedAt и ownerId. Изменить права может только защищённый admin endpoint.

## Административная страница

Маршрут `#admin-users` доступен только admin. Страница содержит поиск по полному email/телефону, пагинацию, карточку пользователя и выбор одной из трёх ролей. Partner назначается автоматически при регистрации.

Администратор видит идентификатор, email, телефон, подтверждение контакта, активность аккаунта и роль. Пароль/хэш, сессии, коды и служебные секреты в этот DTO не входят. Заказы и операционные данные открываются в соответствующих разделах полного административного кабинета.

Доступны смена роли и блокировка/разблокировка аккаунта. Физического удаления пользователя и связанных документов в v1 нет. Произвольное изменение чужого пароля или подтверждённых контактов через эту страницу не добавляется.

Блокировка сохраняет identity и уникальный подтверждённый email. Повторная регистрация этого адреса не создаёт другой аккаунт; восстановление пароля не снимает блокировку и не меняет права. Разблокировать может только admin через защищённое изменение статуса.

| API | Условие и результат |
| --- | --- |
| `GET /api/admin/users?offset=0&limit=24&q=...` | Admin; список с правами и total/offset/limit |
| `GET /api/admin/users/{id}` | Admin; карточка и ETag версии |
| `PATCH /api/admin/users/{id}/permissions` | Admin + Origin + CSRF + If-Match; `{role:"partner"|"operator"|"admin"}` |
| `PATCH /api/admin/users/{id}/status` | Admin + Origin + CSRF + If-Match; `{isActive:boolean}` |

Версия карточки следует auth_version; изменение пароля/прав/активности делает старый If-Match недействительным. Неизвестные поля отклоняются. Устаревшая версия даёт 412 без записи; клиент перечитывает карточку. Ответ содержит только разрешённый административный DTO.

Все изменения прав/активности пишутся в аудит: actor id, target id, прежние/новые роль и активность, время, без контактов и секретов. Admin сразу открывает операционные разделы; назначать себе operator не требуется. Самоназначение привилегий через публичную регистрацию невозможно.

## Проверки и отзыв доступа

Каждый защищённый запрос проверяет User из БД, активность, срок сессии, auth_version и нужное право. Скрытая вкладка или проверка JavaScript не заменяет серверный запрет. По умолчанию доступ закрыт; require_operator разрешает operator и admin, require_admin — только admin.

- Content/catalog presentation/media используют require_admin.
- Shared orders/feedback/notes/conversion, integration health/sync/retry и диагностика уведомлений используют require_operator.
- Личный API заказов/обращений всегда фильтрует owner по User.id; дополнительные права не снимают этот фильтр. Все заказы доступны через отдельный операторский API.
- Существующий обход ответственного по обращению сохраняется для admin, прошедшего общую проверку operator-or-admin. Operator не изменяет назначенное другому оператору обращение через административный обход.
- Изменение прав/активности увеличивает auth_version и отзывает старые сессии. Следующий запрос со старой сессией не выдаёт данные. При изменении собственных прав интерфейс очищает состояние и просит войти заново.
- Уже полученные браузером данные невозможно отозвать. Клиент очищает служебные списки при потере доступа и игнорирует запоздавшие ответы предыдущей сессии.

Нельзя заблокировать последнего активного admin или сменить ему роль. Проверка выполняется под общей транзакционной блокировкой изменений полномочий: две конкурентные операции не могут оставить систему без администратора.

## Видимость прав

Поле role и подписи partner/admin/operator возвращает только `/api/admin/users*`, только авторизованному admin. В обычной сессии нет user.role, списка ролей, бейджа «Партнёр»/«Оператор» или чужих полномочий.

Навигация получает минимальные разрешённые действия/разделы: работа со своим аккаунтом, рабочий кабинет, редактор сайта, управление пользователями. Это необходимо для интерфейса и не обещает скрыть от человека само наличие доступной ему функции. Флаги из браузера не служат основанием серверной авторизации.

DTO ответственного и автора заметки содержит только id и отображаемое имя. Действия над карточкой рассчитываются сервером; FeedbackManager не делает выводы из role других пользователей. Наличие прав не выводится в публичных профилях, списках покупателей или операционной истории.

## Миграция действующей системы

Предлагается переиспользовать нынешнюю identity: Staff/table staff → User/table users с теми же id, password hashes и legacy login. FK сессий, аудита, назначений и заметок переводятся без потери истории. Отдельной Customer identity с собственным паролем не создаётся; owner новых клиентских документов ссылается на User.

Отображение прежних прав, сохраняющее действующий доступ:

- manager → operator;
- действующий admin → admin с полным доступом;
- новый зарегистрированный пользователь → partner;
- новое назначение admin сразу включает операционные возможности.

Матрица подтверждена пользователем. Миграция не сопоставляет legacy login с email и не объявляет выдуманные контакты подтверждёнными. Legacy аккаунту без контактов нужна отдельная проверенная привязка профиля перед клиентским оформлением; служебный вход продолжает работать.

Старые сессии инвалидируются один раз при переходе. Bootstrap создаёт первоначального администратора только при первой установке, определяемой существующим состоянием инициализации; перезапуск не восстанавливает отозванные права. Аварийное восстановление — отдельная локальная команда с явным действием и аудитом. Повторное создание БД, удаление media и down -v не применяются.

## Что меняется и как проверяется

Изменения: auth/bootstrap/manage_staff, ORM/FK/Alembic, все зависимости доступа orders/feedback/integration/content/catalog, HTTP/demo session validators, навигация App и FeedbackManager, новая страница пользователей, OpenAPI/README и fixtures. Простой замены строки manager на operator недостаточно: интеграции сейчас admin-only, а общие заказы доступны обоим staff ролям.

Проверки реализации: три роли для каждого API; partner signup не принимает полномочия; admin видит все служебные разделы, operator не меняет сайт/права; свои документы изолированы; в обычных session/DTO нет ролей; выдача/отзыв на действующей сессии; If-Match конфликт; конкурентное сохранение последнего admin; аудит; миграция стабильных id/FK и прав; bootstrap не возвращает снятые полномочия. Отдельно проверяется, что выдача operator зарегистрированному partner сохраняет его профиль, пароль и собственную историю.

Реализация этих проверок и изменение production не выполнены. SMTP и доступность Telegram остаются отдельными условиями запуска уведомлений.
