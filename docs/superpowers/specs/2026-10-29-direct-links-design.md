# Прямые ссылки на заявки и пункты меню

Статус: дизайн согласован пользователем29.10.2026; реализация прямых ссылок одобрена. Нужны копируемые адреса для меню, открытия в новой вкладке, перезагрузки и кнопок уведомлений. Ссылка задаёт назначение, но не предоставляет доступ к данным.

## Подход

Сохранить существующий hash routing и старые имена `crm`, `case`, `order`. Небольшой общий helper `src/routes.js` отвечает за разбор/сборку адреса; отдельная router-зависимость не нужна. Выбран существующий способ маршрутизации: переход на history paths потребовал бы миграции старых ссылок и конфигурации хостинга. Параметры ссылок идентифицируют ресурс/пункт меню, а не сериализуют формы или контактный поиск.

## Карта адресов

В таблице указан fragment после `https://mirzap67.ru/`; значения ID кодируются через URLSearchParams.

| Назначение | Адрес | Доступ |
| --- | --- | --- |
| Главная, каталог, корзина | `#home`, `#catalog`, `#cart` | Публичный; корзина принадлежит конкретному браузеру |
| Категория | `#catalog?category=oils` | Только доступная публичная категория |
| Товар | `#catalog?product=<ID>` | Только доступный публичный товар; открывается существующий modal |
| Пункт меню с section target | `#home?section=offers` | Существующие значения `offers`, `announcements`, `hot` |
| Публичное объявление | `#home?publication=<ID>` | Только опубликованная доступная карточка, без private CMS read |
| Обращение сотрудника | `#crm-feedback?case=<ID>` | Operator/admin; сохраняет старые адреса |
| Заказ сотрудника | `#crm?order=<ID>` | Operator/admin; сохраняет старые адреса |
| Собственный заказ | `#account-orders?order=<ID>` | Владелец с подтверждённым профилем |
| Собственное обращение | `#account-feedback?case=<ID>` | Владелец с подтверждённым профилем |
| Пользователи / конкретная карточка | `#admin-users`, `#admin-users?user=<ID>` | Только admin |
| Каталог администратора | `#crm-catalog` | Только admin |
| Подменю CMS | `#crm-content?tab=site`, `?tab=publications`, `?tab=media` | Только admin |
| Редактирование объявления | `#crm-content?tab=publications&publication=<ID>` | Только admin |
| Профиль и списки ЛК | `#account`, `#account-orders`, `#account-feedback` | Свой аккаунт |
| Вход с возвратом | `#login?returnTo=<encoded canonical internal hash>` | Вход не ослабляет разрешения назначения |

Прочие существующие верхнеуровневые auth/list маршруты сохраняются. Новые detail endpoints не нужны: HTTP/demo API уже читают товар, заказ, обращение, пользователя и объявление по ID. Для заявок гостя ссылка ведёт в служебную карточку: регистрация не назначает владельца по совпадению телефона/email и не открывает её клиенту.

## Поведение и безопасность

- Один parser/builder — источник URL для меню, landing CTA, карточек товара/категории, заказов, обращений, пользователя и CMS. Ссылки открытия оформляются `<a href>`, операции сохранения остаются кнопками.
- Действительные ID — непрозрачные строки по существующим контрактам:1–128символов, без управляющих символов и специальных `.`/`..`; не вводить глобальный UUID-only формат. Разбор декодирует ID один раз. Известные поля с дубликатами/недопустимыми значениями не вызывают detail fetch; неизвестные поля не попадают в канонический URL.
- Смена категории обновляет URL; открытие товара/заказа записывает detail parameter. Закрытие modal удаляет его, включая прямой вход без родительской history entry. Back/forward и отображаемое состояние совпадают; повторное открытие того же адреса работает.
- Сохранить текущие dirty-form confirmation, возврат фокуса, request counters и очистку данных при logout/смене аккаунта. Отмена перехода восстанавливает принятый адрес вместе с видимым состоянием.
- На холодном входе сначала загрузить нужный ID независимо от текущей страницы списка. Ссылки на section/publication ждут загрузки публичного сайта и DOM перед scroll/focus. Отсутствующая/скрытая запись отображается как недоступная, не подменяется другой карточкой.
- Если требуется вход, сохранить безопасное назначение в `returnTo` и передать его через login/signup/activation/password reset и необходимое завершение профиля. После успешной сессии/профиля открыть исходное назначение. Результаты старой сессии не применяются к новой.
- `returnTo` — только канонический внутренний hash из allowlist: без внешнего origin, `//host`, path URL, auth destination, рекурсивного returnTo, управляющих символов и неизвестной страницы. Восстановление всегда через parser→builder→hash navigation, не через присваивание произвольного `location.href`. Неверный returnTo выбирает текущую безопасную страницу по роли.
- Сервер по-прежнему проверяет роль и customer_id на каждом GET. Partner не получает CRM/API, чужой или гостевой ресурс клиента даёт404. Защищённый компонент не монтируется для неподходящей роли. GET-ссылка не выполняет принятие в работу, смену статуса, назначение прав или иные мутации.
- В URL и returnTo не помещаются контакты, текст обращения, адрес доставки, password/OTP, session/CSRF token или точный контактный поиск. Прямые ссылки не являются magic login или bearer-ссылками.

## Кнопки internal-notifier

Backend формирует URL из доверенного PUBLIC_SITE_URL и typed destination: например staff feedback либо staff order. Пользовательское поле URL/Host не служит источником ссылки. Часть `#...` обрабатывается браузером и не попадает в HTTP request path; серверные access logs не заменяют события просмотра SPA.

Формат маршрутов синхронизируется с внешней per-source URL policy. Для MIRZAP разрешаются только нужные страницы и соответствующие ID/enum поля; внешние origin, userinfo, произвольный top-level query, токены и неизвестные fragment параметры запрещены. Старый `#crm-feedback?case=<UUID>` продолжает приниматься. Новые автоматические типы уведомлений не включаются этим изменением; подготовлены адреса, на которые они смогут ссылаться.

JS и Python используют небольшие собственные builders; таблица совместимых примеров и отказов в тестах связывает их формат без runtime-DSL. Бизнес-данные читаются только сайтом после авторизации; в Telegram отправляются номер/тип/время и кнопка.

## Где изменится код

`src/routes.js` и `App.vue`; URL controls в `LandingPage`, `ProductCard`, `FeedbackManager`, `CustomerAccount`; selection/tab props в `UsersManager` и `ContentManager`; auth continuation в `AccountAccess`. На backend — helper ссылок и использование его существующим feedback emitter. Внешний notifier получает новую URL policy как часть handoff; его сервер здесь не реализуется.

## Приёмка

1. Round-trip адресов и старых feedback/order URLs; ID с пробелами/Unicode/`?&#%`; неверные/дублированные/overlong/control параметры.
2. Безопасный auth return: сохранение назначения при login/reload/profile completion; отказ внешних/рекурсивных/auth targets.
3. Меню/карточки: новая вкладка, reload, modal open/close/reopen, back/forward, холодный scroll после async site.
4. Staff/customer deep detail вне текущей страницы списка;403/404 на неверной роли/владельце, нет утечки старого аккаунта.
5. Dirty-form отклонение перехода, поздние ответы и logout не меняют новую карточку.
6. Согласованный backend URL/внешняя allowlist; только доверенный origin, отсутствие контактов/токенов, неизменность уже сохранённых snapshots.
