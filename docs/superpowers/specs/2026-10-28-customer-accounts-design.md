# Личный кабинет покупателя MIRZAP67

Дата: 28.10.2026. Статус: проект для проверки и согласования; реализация не начата.

## Подтверждено пользователем

- Нужны заметные кнопки «Войти» и «Зарегистрироваться», личный кабинет покупателя и существующий кабинет администратора.
- Регистрация: телефон, email и пароль, который выбирает пользователь; активация через код из письма.
- В перспективе нужен вход по телефону или email и подтверждение через email, Telegram, при необходимости платные SMS.
- Заказ гостя не принадлежит аккаунту, даже если его телефон/email совпадают с зарегистрированными контактами.
- У вошедшего покупателя контакты берутся из профиля на сервере: повторно вводить их при заказе не требуется.
- Заказы вошедшего покупателя и их статусы должны быть видны в его кабинете.
- Персональные данные должны храниться зашифрованными.
- SMTP-провайдера у пользователя пока нет.
- Первый этап: вход по почте и паролю; вход по телефону отложен до подтверждения номера (отдельно подтверждено пользователем).
- Нужна страница пользователей/прав: новые регистрации — партнёры; администратор автоматически имеет полный доступ, включая возможности оператора, редактирует сайт и назначает права. Права/статусы видит только администратор.

## Рассмотренные способы входа

| Подход | Результат обсуждения |
| --- | --- |
| Собственный пароль и первоначальное подтверждение email кодом | Выбран пользователем: после активации вход не требует нового письма каждый раз |
| Одноразовый код при каждом входе без пароля | Рассмотрен; пользователь уточнил, что пароль задаёт сам, поэтому этот вариант не реализуется |

## Предложения для первой версии, требующие согласования

- Единая User identity, один пароль и одна UserSession заменяют разделение Customer/Staff; отдельный сервис идентификации не требуется.
- Иерархия хранится одним `User.role`: `partner | operator | admin`; admin включает operator, а operator включает покупательские возможности партнёра. Независимые grant-флаги не нужны.
- Оба контакта обязательны при регистрации. Подтверждённый email уникален, непроверенный телефон не уникален.
- Telegram/SMS не входят в первую реализацию: существующий бот уведомляет команду магазина, а не подтверждает покупателей.
- Кабинет покупателя показывает собственные заказы и обращения, позволяет создать обращение с контактами профиля.
- Заказы/обращения доступны покупателю только для чтения; управление статусами остаётся у сотрудников.
- Восстановление пароля — кодом на подтверждённый email. Редактирование контактов и привязка старых гостевых данных в v1 не нужны.
- Поиск сотрудников по контактам — только по полному нормализованному телефону/email; поиск по номеру заказа/обращения сохраняется.

## Что уже есть и что сохраняем

FastAPI, PostgreSQL, SQLAlchemy и Alembic уже обслуживают API; Vue использует hash-маршруты и собственный HTTP-клиент.
`backend/app/auth.py` содержит Argon2, случайные серверные сессии, CSRF, проверку Origin и ограничение попыток входа.
Сейчас Staff имеет роли `manager`/`admin`; миграция переводит существующие идентичности в User, без дублирования credentials при выдаче новых прав.
Матрица: `/api/manager/*` со служебными данными допускает role=operator или admin; `/api/admin/*` для сайта/пользователей — только admin. Legacy session-маршрут — совместимый способ входа.
Новая страница пользователей дополняет существующий интерфейс; матрица доступа и выдача прав описаны в [дизайне прав пользователей](2026-10-28-user-permissions-design.md).
Все handlers проверяют право явно, а не просто факт входа; новые регистрации не получают служебный доступ автоматически.
Принятие заказа, резерв и ERP-outbox остаются одной транзакцией; версия/`If-Match` и проверки каталога сохраняются.
Без адаптера 1С реальный заказ по-прежнему получает `503 ERP_NOT_CONFIGURED`: это отдельное ограничение, независимо от аккаунтов.

## Публичный интерфейс и кабинет

В верхней части сайта появляются «Войти»/«Зарегистрироваться»; после входа — «Личный кабинет».
На экране входа остаётся ссылка для legacy-логина сотрудников; она использует того же User и пароль, без второго аккаунта/сессии.
Новые hash-маршруты: `#login`, `#signup`, `#activate`, `#password-reset`, `#account`, `#account-orders`, `#account-feedback`.
Экран регистрации содержит только телефон, email и пароль; адрес доставки и ФИО при регистрации не собираются.
После отправки формы показываем ввод кода, безопасное сообщение о доставке, таймер повторной отправки и возможность начать заново.
Профиль показывает email как подтверждённый и телефон с явной пометкой «Не подтверждён».
Для legacy-пользователя без контактов экран предлагает однократно заполнить реальный телефон/email и подтвердить email; до этого оформление из профиля недоступно.
При оформлении вошедший пользователь видит контакты профиля; имя необязательно, пустое имя допустимо, искусственные значения не подставляем. Служебное отображаемое имя legacy-аккаунта не копируем в новые клиентские контакты: в обращении имя пустое, в заказе используем только явно указанное необязательное имя.
Гостевая форма сохраняет имеющиеся контакты/имя; способ получения и адрес доставки остаются свойствами конкретного заказа.
При истёкшей сессии сохраняем корзину/форму и предлагаем снова войти; заказ автоматически в гостевой режим не переводим.
Списки кабинета имеют загрузку, пустое состояние, ошибку, повтор запроса и пагинацию; детали доступны по собственной ссылке.
Выход и смена аккаунта сразу очищают загруженные заказы/обращения и секретные поля; запоздавшие ответы старой сессии игнорируются.
Существующие диалоги, поля, индикаторы ошибок, адаптивные стили и клавиатурная доступность переиспользуются.

## Хранение аккаунта и владения

- `User`: стабильный id, ciphertext профиля, HMAC-индекс email, password_hash, email_verified_at, is_active, role, created_at, auth_version; role ограничен `partner | operator | admin` в API и CHECK БД.
- Nullable legacy_login с собственным ciphertext/lookup и необязательное display_name сохраняют прежние данные; email/подтверждение из них не выдумываем.
- Профиль содержит email и телефон без обязательного имени/адреса; новый User всегда role=partner, телефон не подтверждён и не даёт право входа.
- Новый User создаётся после активации; pending-регистрация хранится отдельно и не переписывает существующего User.
- `UserSession`: id, user_id, token_hash, expires_at, auth_version; одна сессия обслуживает личный и разрешённые служебные разделы.
- `UserChallenge`: flow_id, purpose, continuation_hash, code_hmac, generation, encrypted_payload, created_at, expires_at, attempts, consumed_at.
- Pending payload регистрации содержит только нормализованные контакты и Argon2-хэш выбранного пароля; исходный пароль не сохраняется.
- Назначение challenge — `signup`, `password_reset` или `profile_completion`; коды разных назначений невзаимозаменяемы.
- Долговечные счётчики ограничивают выдачу/проверку по HMAC email, IP и конкретному flow.
- В `orders` и `feedback` добавляются nullable indexed FK `customer_id -> users.id`; существующие гостевые строки остаются NULL.
- FK покупателя не каскадно удаляет заказы/обращения; удаление аккаунтов не входит в эту версию.
- Вошедшее создание берёт customer_id=User.id и контакты из серверного активированного профиля, независимо от дополнительных прав.
- При конверсии обращения в заказ переносим customer_id обращения; у гостевого обращения он остаётся NULL.
- Совпадение контактов никогда не назначает владельца и не открывает исторические гостевые документы.

## Нормализация, уникальность и гонки

Email: обрезать внешние пробелы, проверить длину/синтаксис и привести к единой lowercase-форме до индексации и сравнения.
Это выбранная политика идентификаторов проекта, а не заявление о регистронезависимости всех почтовых систем.
Телефон: существующая проверка российского номера и каноническое `+7` + 10 цифр; непроверенный телефон не даёт права доступа.
Телефон не резервирует идентификатор и не блокирует регистрацию другого владельца email.
Индексы равенства — HMAC от нормализованного значения с отдельным доменом для каждого вида поля, не обычный SHA-256 контакта.
Уникальность подтверждённого email обеспечивает ограничение БД для всех User, включая заблокированные is_active=false; конкурентные активации проверяются в одной транзакции. Неподтверждённый legacy login не резервирует email.
Повторная регистрация существующего email, включая заблокированный аккаунт, не создаёт заменяющую identity и не меняет пароль, профиль, права, активность или сессии существующего User.
Каждое новое начало регистрации получает собственные flow/continuation; повторная анонимная заявка не переписывает чужой pending payload.
Владелец почты может начать собственную регистрацию, даже если ранее чужой браузер создал pending flow с его email.
Активируется только payload того flow, для которого предъявлены правильные код и browser continuation; код другого flow не подходит.
Первое успешное подтверждение создаёт User; проигравший конкурентный flow не обновляет аккаунт и получает безопасный результат без 500.
Для уже занятого email, включая заблокированный аккаунт, signup возвращает ту же внешнюю форму ответа с неприменимым opaque flow, без признака существования аккаунта.
Legacy-логин использует отдельный namespace и прежнюю нормализацию; он не становится подтверждённой email identity и не служит основанием слияния аккаунтов.

## API: единая аутентификация

Все маршруты ниже имеют префикс `/api/customer`; ошибки используют существующий безопасный контракт API.
Публичные POST проверяют допустимый Origin; cookie-авторизованные изменения дополнительно требуют CSRF общей UserSession.

| Метод и путь | Тело / результат |
| --- | --- |
| `POST /auth/signup` | `{email, phone, password}` → `202 {flowId, resendAfterSeconds}` и continuation-cookie |
| `POST /auth/activate` | `{flowId, code}` + continuation → `200` UserSession; атомарная активация партнёра |
| `POST /auth/resend` | `{flowId}` + continuation → generic `202`, без изменения pending профиля/пароля |
| `POST /session` | `{email, password}` → `200` UserSession, по реальному подтверждённому email активного User |
| `GET /session` | общая cookie → `200 {user:{id,email,phone,emailVerified,phoneVerified:false,profileComplete},capabilities,csrfToken,expiresAt}` |
| `DELETE /session` | Origin + CSRF → `204`, отозвать сессию и удалить cookie |
| `POST /auth/password-reset` | `{email}` → generic `202 {flowId,resendAfterSeconds}` и continuation-cookie |
| `POST /auth/password-reset/confirm` | `{flowId,code,newPassword}` + continuation → `204`, сменить хэш и отозвать все сессии User |
| `POST /profile/activation` | `{email,phone}` + UserSession/CSRF → `202 {flowId,resendAfterSeconds}`, purpose=profile_completion |
| `POST /profile/activation/confirm` | `{flowId,code}` + та же User identity/CSRF/continuation → `200` обновлённая UserSession |

Логин возвращает одинаковую ошибку для неизвестной почты, неверного пароля и отключённого аккаунта; используется dummy Argon2 verify.
Пароль: предлагаемый минимум 12, максимум 256 символов; не trim, не усекать, разрешать вставку и password manager.
Единая cookie `lavr_session` сохраняет существующее техническое имя: Secure на HTTPS, HttpOnly, SameSite=Strict, Path=/api, срок 8 часов.
Continuation-cookie отдельная, случайная, HttpOnly/Secure/SameSite=Strict, живёт не дольше flow и не даёт доступ к аккаунту.
CSRF привязан к UserSession; каждый запрос повторно проверяет is_active/auth_version и нужное право, дополнительная staff-cookie не создаётся.
Успешный вход/активация меняют токен; смена пароля/прав/активности увеличивает auth_version, отзывая и конкурентно созданные прежние сессии.
Session DTO не содержит raw role/grant/status; сервер выводит capabilities для навигации из role. Просмотр/смена canonical role и статусов доступен только admin users API.
role, capabilities, is_active, ownerId/customerId, verifiedAt и другие служебные поля в публичном input запрещены; admin users API PATCH принимает role только из canonical enum.
`/api/manager/session` при сохранении legacy-входа использует того же User, хэш, cookie, CSRF и отзыв; это не обход operator/admin-проверок API.
Legacy User без проверенных контактов входит по прежнему логину только в доступные служебные разделы и экран завершения профиля.
Profile completion привязывает immutable challenge к уже вошедшему User/auth_version и проверяет уникальность email; обновляет ту же identity без нового аккаунта/пароля/прав.
Совпадение email с другим User не объединяет их; после подтверждения профиль дополняется реальными контактами, сессия ротируется. Обычное редактирование контактов остаётся вне v1.

## Коды и доставка писем

Код — 6 случайных цифр из криптографического генератора; в challenge хранится только HMAC(purpose, flow_id, generation, code).
Ключ HMAC не хранится в БД и отличается от SESSION_SECRET; сравнение constant-time.
Предлагаемые лимиты: срок кода 10 минут, жизнь flow 30 минут, не более 5 неверных проверок flow.
Повторная отправка — не раньше 60 секунд; совокупно не более 5 писем/email и 20/IP в час, 20 проверок/email и 60/IP в час.
Счётчики и Retry-After долговечны; IP берётся через существующую проверку доверенного proxy, не из произвольного forwarded-заголовка.
Resend требует continuation, увеличивает generation, меняет код, но не восстанавливает исчерпанные попытки и не продлевает жизнь flow.
Срок нового кода ограничен меньшим из now + 10 минут и created_at flow + 30 минут; проверка отсутствующего/неактивного flow одинаково безопасна.
Чтение/проверка/consume выполняются под блокировкой; параллельный правильный код создаёт ровно один аккаунт/одну смену пароля.
Код, continuation и пароль никогда не возвращаются в JSON, логах, метриках или браузерном storage.
Смена/reset пароля не меняет профиль/права/is_active и не активирует pending-регистрацию; profile_completion не меняет пароль/права. Для заблокированного User recovery возвращает generic ответ без создания применимого challenge; signup/recovery не обходят административную блокировку.

SMTP — один конкретный транспорт на стандартных `smtplib`, `email.message`, `ssl`, с таймаутом и проверкой TLS-сертификата.
Настройки: SMTP_HOST, SMTP_PORT, SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM, SMTP_TLS_MODE=starttls|tls; незашифрованной отправки нет.
Challenge и событие `customer_verification_email` в существующем Outbox коммитятся одной транзакцией.
Письма отправляет отдельный процесс `python -m app.email_worker`, выбирающий только этот event_type. Он не зависит от TELEGRAM_NOTIFICATIONS_ENABLED и не обрабатывает Telegram/ERP события. В Compose добавляется сервис `verification-emails` из backend image с профилем `customer-email`, включаемый явно после настройки SMTP; ему передаются БД, ключи шифрования и SMTP, без токена Telegram.
Payload письма (получатель, код, текст, flow/generation) шифруется; открытого OTP или email в outbox не остаётся.
Worker перед отправкой проверяет, что challenge ещё жив, не consumed и generation актуальна; устаревшие задания не отправляет.
Повтор SMTP-доставки отправляет тот же код, не создаёт новую регистрацию; возможное дублирование письма допустимо.
Обработка ошибок сохраняет только безопасные коды, использует существующие lease/retry-подходы; OTP не попадает в last_error_code.
Результат API сообщает о принятии отправки, но не утверждает, что SMTP-провайдер уже доставил письмо.
Никакого универсального интерфейса провайдеров, Telegram/SMS-заглушек или вывода production-кода в консоль.
Encrypted payload доставленного/отменённого письма удаляется; просроченные pending payload и code_hmac очищаются не позже суток после окончания flow. Минимальные метаданные и throttle-счётчики остаются только на срок своего окна; cleanup выполняет тот же email worker и проверяется тестами.

## API: заказы и обращения

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/customer/orders?offset=0&limit=24` | Только собственные заказы, total/offset/limit |
| `GET /api/customer/orders/{id}` | Собственный заказ либо 404, включая чужой id |
| `POST /api/customer/orders` | `{fulfillment,items,name?}` + Origin/CSRF/Idempotency-Key; контакты из профиля |
| `GET /api/customer/feedback?offset=0&limit=24` | Только собственные обращения |
| `GET /api/customer/feedback/{id}` | Собственное обращение либо 404 |
| `POST /api/customer/feedback` | `{type,message}` + Origin/CSRF/Idempotency-Key; контакты из профиля |

Customer order DTO: id, number, createdAt, status, totalKopecks, items, fulfillment; без externalDocumentId и технических ERP-состояний.
Customer feedback DTO: id, number, createdAt, type, message, status, связанная customer order receipt при наличии.
В customer DTO не входят внутренние resolution, заметки, история сотрудников, назначение, аудит и Telegram-диагностика.
Маршруты `/api/customer/orders|feedback` — проекции собственных записей любого User с активированным полным профилем, включая admin/operator; иначе 409 PROFILE_REQUIRED.
SQL list/detail всегда фильтруются по customer_id=User.id сессии; знание номера/id и совпавших контактов недостаточно.
Общий build_order принимает данные из доверенного customer/guest адаптера; проверки цен/остатков/резервов не дублируются.
Обязательность `CustomerInput.name` снимается только для customer-пути и его сериализатора; гостевая валидация имени сохраняется.
Гостевые `/api/orders` и `/api/feedback` остаются гостевыми; с валидной lavr_session дают 409 CUSTOMER_FLOW_REQUIRED без записи, включая legacy User без профиля.
Фронтенд вошедшего покупателя сразу выбирает `/api/customer/*`; редирект POST с PII и повторная отправка от имени гостя не применяются.
Истёкшая/невалидная предъявленная lavr_session на любом пути создания даёт 401, а не незаметное создание гостевой записи.
Чтобы отправить как гость после истечения cookie, пользователь явно выходит/очищает её через разрешённый same-origin logout.
Гостевой logout допускает очистку истёкшей cookie с Origin-проверкой, не открывая доступ к данным и не требуя живой сессии.
Ключ идемпотентности остаётся уникален внутри типа операции; запись хранит actor (`guest` или User.id) и immutable owner результата.
Replay не меняет владельца; чужой actor получает безопасный конфликт, а не прежний заказ/обращение.
Дайджест включает actor; фронтенд ограничивает область сохранённой попытки аккаунтом и сбрасывает её при смене идентичности.
Совместимость старых повторов задаётся явно: существующие attempt/feedback получают actor=guest и digest_version=1, их digest не переписывается. При гостевом replay используется прежняя канонизация тела без actor. Новые записи получают digest_version=2 с actor; проверка владельца выполняется до выдачи receipt. Чужой customer не может воспользоваться веткой legacy guest; версия не выбирается клиентом. Миграционный тест повторяет уже принятые guest order/feedback с исходным ключом и получает прежнюю квитанцию.
Гостевой replay после входа не становится заказом аккаунта; гостевые записи никогда не присваиваются автоматически.

## Шифрование персональных данных

Используем AES-256-GCM из `cryptography`: новой зависимости здесь соответствует необходимая проверенная реализация AEAD, не самописная криптография. Аутентифицированное шифрование соответствует [рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).
На каждое шифрование генерируется свежий 96-bit nonce; envelope содержит версию формата, key_id, nonce и ciphertext с tag.
AAD связывает ciphertext с таблицей, id записи, полем и версией; повреждение/перестановка приводит к безопасной ошибке, не к fallback plaintext.
Ключ шифрования и отдельный ключ HMAC-индексов выдаются серверу извне БД, отличаются от SESSION_SECRET и не имеют небезопасных defaults.
Backend, migration и worker получают нужные ключи серверно; в VITE_*, образах, git и браузере их нет.
Key_id сохраняем для управляемой ротации; универсальный KMS/фреймворк управления ключами в v1 не строим.

Шифруются все копии клиентских данных, а не только новый профиль:

- User profile, legacy login/display_name и pending payload, получатель/код/текст verification email в outbox.
- `Order.customer`, `Order.fulfillment.address`, соответствующие customer/fulfillment в ERP `Outbox.payload` (`orders.py:208-213`).
- `Feedback.name/phone/email/messenger/message/resolution`, `FeedbackNote.text` (`feedback.py:44-70`).
- `Feedback.conversion_response`: текущий snapshot содержит контакты, message/resolution и историю с заметками (`feedback.py:237,361`).
- Иные persisted snapshots/outbox-поля с теми же данными при обходе модели; публичные product/media/site данные не шифруются ради этого требования.

Пароли остаются Argon2-хэшами; токены сессий/continuation — хэшами, коды — keyed HMAC, а не обратимо зашифрованными паролями. Различие хранения паролей и обратимого шифрования описано в [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
Старые plaintext-контакты удаляются из рабочих колонок после проверенного backfill; plaintext-дубли для поиска запрещены.
Сотрудники ищут полный телефон/email через HMAC-индексы, номер через существующее поле; поиск по имени/частям контакта убирается из UI и API.
Внешний ERP получает расшифрованные нужные поля только при авторизованной отправке; повторное чтение outbox сохраняет прежнюю транзакционность.
API сохраняет Cache-Control:no-store; body, коды, email, телефоны и SMTP credentials не попадают в access/error logs и traces.
Шифрование БД не ограничивает законный доступ CRM к расшифрованным данным и не заменяет TLS, роли и фильтрацию владельца.

## Миграция, запуск и откат

Новая Alembic-миграция после 0003 переименовывает staff → users, переводит role на canonical enum, добавляет профиль/challenge/throttle/ownership/ciphertext/lookup и переводит staff_sessions в UserSession.
ID/Argon2-хэши сохраняются; FK аудита, заметок и назначения обращения переводятся на users без потери истории. Старые сессии однократно отзываются.
Миграция ролей: прежний manager → operator, прежний admin → admin с сохранением полного доступа. Новая выдача admin автоматически открывает также операционные возможности.
Legacy email/телефон остаются NULL до реального завершения профиля; bootstrap не восстанавливает отозванные права и не создаёт вторую identity при перезапуске.
До запуска: защищённый согласованный backup PostgreSQL/media, отдельное защищённое хранение ключей и проверка восстановления на копии.
На согласованное окно останавливаем запись и worker, выполняем backfill существующих PII, проверяем полноту, затем запускаем совместимый релиз.
Backfill включает feedback notes/conversion snapshots и ERP outbox; ошибка/отсутствие ключа останавливает переход, plaintext не теряется молча.
Текущий CHECK `status != 'closed' OR length(trim(resolution)) > 0` заменяется при шифровании resolution: непустое основание закрытия проверяется до шифрования в сервисе.
Переходы статуса проходят единый валидатор; закрытый статус без валидного расшифрованного resolution не допускается, invariant покрывается тестом миграции и API.
Сверяем число записей, расшифровку и ключевые CRM/ERP сценарии; старые guest customer_id остаются NULL без поиска совпавших контактов.
Новые backups защищаются отдельно от ключей; старые plaintext backups остаются чувствительными до удаления по согласованному сроку хранения.
Не используем `docker compose down -v`, пересоздание production БД или удаление существующих media/volume как способ миграции/отката.
Откат до открытия записи возможен на проверенный backup/старый релиз; после открытия нельзя терять новые записи восстановлением старой копии.
После открытия записи предпочтителен исправленный совместимый релиз; возврат старой схемы требует явной обратной миграции с ключами и проверки данных.
Демо-режим сохраняет явную маркировку и не имитирует реальную отправку писем/подтверждённый production-аккаунт.

Конкретный блокер публичного включения: выбрать SMTP-сервис, подтвердить отправителя/домен, получить настройки и проверить реальное письмо.
`CUSTOMER_REGISTRATION_ENABLED` по умолчанию false; без работоспособного SMTP signup/recovery дают 503, production-код нигде не показывается.
Флаг регистрации управляет созданием новых аккаунтов; его выключение не отключает вход существующих клиентов и восстановление их пароля при рабочем SMTP. Остановка Telegram worker не препятствует доставке писем.
Подготовка кода и тесты возможны до SMTP; включение живой регистрации выполняется после настройки транспорта и проверки на HTTPS.

## Критерии приёмки

1. Signup с выбранным паролем → письмо → верный код → активный аккаунт; без активации входа/данных нет, код не виден в API/логах.
2. Дубликат active/pending signup и resend не меняют чужой пароль/профиль; две конкурентные активации не создают дубли email.
3. Неверные/истёкшие/старой generation/уже consumed коды не проходят; гонка consume и обход лимитов через новый flow проверены.
4. Партнёры не читают чужие списки/детали и не назначают role/owner; operator допускает служебные маршруты, admin также получает их и users/site, одна UserSession не заменяет role-проверку.
5. Совпавшие контакты гостя не дают владения; конверсия signed-in обращения сохраняет customer_id, гостевого — NULL.
6. Вошедший заказ использует профиль без повторного ввода контактов/обязательного имени; адрес только из оформления, статус виден в ЛК.
7. Истёкшая cookie не создаёт гостевой заказ; replay и запоздавший ответ после смены аккаунта не раскрывают/не присваивают чужой документ.
8. Customer DTO не содержат внутренних заметок/resolution/audit/Telegram; новые обращения используют профиль и видны в CRM.
9. Reset требует код и continuation, меняет только пароль и отзывает все сессии этого User в личных/служебных разделах; другие User не затрагиваются.
10. Сырые SQL-данные всех перечисленных PII копий не содержат исходных контактов/текстов; повреждённый ciphertext отклоняется, crypto round-trip проверен.
11. Падение SMTP/worker/commit не активирует аккаунт без подтверждения и не теряет согласованность challenge/email; повтор письма безопасен.
12. Миграция проверена на копии с существующими заказами/заметками/outbox, точный поиск и backup restore работают; volume не удаляются.
13. Выдача/отзыв прав не создаёт identity/пароль/вторую auth-cookie; legacy-вход сохраняет User.id, завершение профиля подтверждает реальный email до покупки без выдачи новых прав.
