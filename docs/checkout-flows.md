# Два сценария оформления заказа

Сейчас реализуется заказ с самовывозом без онлайн-предоплаты. Второй сценарий —
онлайн-оплата через банк — проектируется для следующего этапа.

| Часть формы | Самовывоз без онлайн-оплаты — сейчас | Онлайн-оплата — следующий этап |
| --- | --- | --- |
| Товары | Общая корзина, количество, актуальные цены и итог | Та же корзина и проверки сервера |
| Контакты гостя | Имя, телефон, необязательный email | Те же контакты |
| Пользователь с аккаунтом | Подтвержденные контакты из профиля, необязательное имя для заказа | Те же правила профиля |
| Получение | Самовывоз, адрес и часы магазина из настроек сайта | Хранится отдельно от способа оплаты; самовывоз можно сохранить |
| Оплата | В магазине, без ввода платежных данных на сайте | Переход на платежную страницу банка |
| Основная кнопка | «Заказать с самовывозом» | «Перейти к оплате» |
| Подтверждение | Номер заказа, сумма, самовывоз; менеджер согласует выдачу | Номер заказа и подтвержденный сервером результат оплаты |

## Текущая форма

После корзины покупатель вводит контакты и видит информацию о самовывозе.
Выбора доставки и поля адреса покупателя нет. Сервер также отклоняет новые
storefront-заказы с доставкой: `422 FULFILLMENT_UNAVAILABLE`. Это правило общее
для гостевого оформления и личного кабинета.

Запрос сохраняет привычный формат `fulfillment: {method: 'pickup', address: ''}`.
Старые квитанции, история и идемпотентные повторы ранее сохраненных заказов
с доставкой остаются доступны. Менеджерская конверсия обращения не ограничивается
новой политикой формы магазина.

Успешное оформление создает заказ и резерв, очищает корзину и показывает
подтверждение самовывоза. Менеджер получает Telegram-уведомление и подтверждает
наличие/время выдачи. Порядок обработки, отмена и остатки описаны в
[manual-orders.md](manual-orders.md).

## Будущая форма с оплатой

Форма использует ту же корзину и контактные правила, но добавляет платежный шаг.
После проверки суммы сервер создает платежную попытку для существующего заказа
и получает ссылку банка. Покупатель вводит реквизиты на стороне банка.

Оплата и обработка заказа — разные состояния. Новый статус платежа нельзя
подменять `Order.status` или статусом обмена с 1С. Оплаченный заказ еще может
ожидать подтверждения магазина и подготовки к выдаче.

Для прежних заказов с оплатой в магазине банковские попытки задним числом
не создаются. Завершенный заказ сам по себе не подтверждает банковский платеж.

Возврат покупателя из банка открывает страницу результата и запрашивает статус
у сервера. Основанием для «Оплачено» служит проверенное серверное подтверждение
банка. Повторное уведомление банка или обновление страницы не должны создавать
другой заказ, резерв или повторную оплату. При отмене/ошибке оплаты показывается
фактический результат и доступное действие для того же заказа.

Банк, его API, правила платежных попыток и сроки резерва согласуются при подключении
интеграции. До этого этапа платежные поля, переключатель типа заказа и кнопка
оплаты в действующем интерфейсе не появляются. Платежные таблицы и банковские
заглушки сейчас не добавляются.
