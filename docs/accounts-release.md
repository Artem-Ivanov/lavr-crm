# Выпуск аккаунтов и прав доступа

Это инструкция для подготовленного локального кандидата. Она не означает, что production обновлён: SMTP ещё не настроен, регистрация должна оставаться выключенной. На VM `157.228.139.156` исходящий доступ к Telegram заблокирован; отдельное подключение описано в [runbook relay](telegram-relay-runbook.md). Команды ниже выполняются оператором при согласованном выпуске, не являются разрешением отправлять письма или уведомления.

## Права и кабинет

| Роль в admin API | Возможности |
| --- | --- |
| `partner` | Новый подтверждённый аккаунт по умолчанию; свой профиль, собственные заказы и обращения |
| `operator` | Возможности покупателя и работа с заказами, обращениями и операционным обменом |
| `admin` | Полный доступ: возможности оператора, каталог, сайт, медиа и управление пользователями |

Новые регистрации никогда автоматически не становятся сотрудниками. Историческая миграция `0004` переводит прежний `manager` в `operator`, оставляет `admin` администратором и сохраняет идентификаторы, пароль и legacy-логин; только этот переход отзывает прежние сессии. Текущий переход `0005` → `0006` сохраняет действующие сессии. Назначенная роль и активность видны только администратору через `/api/admin/users`; общая сессия возвращает `capabilities.operate/editSite/manageUsers`, без `role` и `isActive`. Страница `/#admin-users` и вкладка «Пользователи» доступны только администратору. Изменения роли/активности требуют CSRF и `If-Match`, отзывают прежние сессии; последнего активного администратора отключить или понизить нельзя.

Вход по подтверждённому email и паролю: `/#login`; регистрация: `/#signup`; кабинет: `/#account`. Прямые ссылки на служебные страницы показывают ту же форму email и сохраняют исходное назначение. Старые имена пользователя больше не используются для входа: совместимое поле `login` в `/api/manager/session` принимает email и использует ту же проверку и throttling, что `/api/customer/session`. В административном API `login` равен `email`, отдельного пользовательского идентификатора нет. Сотрудник без подтверждённых контактов сначала завершает профиль, чтобы оформлять собственные заказы. Телефон пока не подтверждён и не используется для входа. Совпадение контактов с гостевым заказом/обращением не назначает владельца: исторические гостевые строки остаются гостевыми. Собственные записи доступны только своему аккаунту; контакты и владелец новых записей берутся сервером из профиля. Гостевые POST с предъявленной действующей сессией возвращают `409 CUSTOMER_FLOW_REQUIRED`, с истёкшей — `401`, без автоматического перехода к гостю.

Перед production-переходом на единый вход проверьте наличие подтверждённого email у всех нужных сотрудников, включая хотя бы одного активного администратора. Историческим пользователям без email адрес автоматически не присваивается. Завершите подтверждение профиля в действующей сессии до перехода; для письма нужен настроенный SMTP. Существующие ID, хэши паролей, роли и сессии при обновлении сохраняются. Новая установка получает email администратора из явно заполненного `ADMIN_LOGIN`; bootstrap не изменяет существующие учётные записи. Серверная команда создания оператора также требует email и считается доверенным ручным provisioning.

Миграция `0006` переводит канонические номера обращений обоих типов в общую целочисленную последовательность по `created_at, id`. UUID и ссылки сохраняются. Публичные квитанции и идемпотентные ответы, сохранённые до миграции, содержат прежний строковый номер и возвращаются без переписывания; актуальные списки и карточки показывают новый целочисленный номер. Снимки уже отправленных уведомлений также сохраняются. Обновление требует резервной копии и применения миграции в обычном окне обслуживания; frontend нужно обновлять вместе с backend.

Аккаунты не включают реальный обмен 1С: без адаптера оформление по-прежнему возвращает `503 ERP_NOT_CONFIGURED`. Резерв, цена, outbox, версии и ручные бизнес-переходы сохраняют прежние правила.

## Новая установка

Локальная новая база запускается `./scripts/start.sh`. Скрипт создаёт приватный `.env.docker` через `python -m app.init_env`, включая независимые случайные пароли, `SESSION_SECRET`, `PII_ENCRYPTION_KEYS`, `PII_INDEX_KEY` и `CHALLENGE_SECRET`. Существующий env он не дополняет и не заменяет. До запуска сохраните секреты вне сервера/образов; не используйте этот способ как обновление существующей базы без раздела ниже.

Для новой HTTPS-установки сначала соберите backend и создайте env без запуска сервисов:

```sh
umask 077
docker build -t lavr-crm-backend:local backend
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true --entrypoint python lavr-crm-backend:local -m app.init_env > .env.docker.new
```

Убедитесь, что `.env.docker` ещё не существует, затем переместите новый файл в `.env.docker`. До первого запуска заполните `ADMIN_LOGIN` действующим email администратора, задайте production-параметры HTTPS по README, `SEED_DEMO_CATALOG=false`, `CUSTOMER_REGISTRATION_ENABLED=false`, `TELEGRAM_NOTIFICATIONS_ENABLED=false`. Сохраните защищённую копию env. В новой пустой базе миграции `0001`–`0006` применяются при запуске backend; специальное разрешение на PII-backfill не требуется.

## Обновление существующей базы: только в окно обслуживания

`0004` шифрует существующие профили, контакты/адреса/снимки заказов, обращения, заметки и персональные payload outbox; переносит `staff`/сессии в `users`/`user_sessions`. `0005` добавляет challenge и долговечные лимиты email-подтверждения. `0006` переводит текущие номера обращений в общую числовую последовательность. Для базы до `0004` без подтверждённых email сначала нужен промежуточный релиз с завершением профиля и прежним способом входа; прямой переход на email-only релиз оставит таких сотрудников без нового входа. Обычный запуск backend сам выполняет `alembic upgrade head`, поэтому сначала проверьте email сотрудников, остановите writers и подготовьте ключи. PostgreSQL остаётся запущенным. Не запускайте новый backend параллельно со старым приложением, SMTP-, Telegram- или ERP-worker.

1. Сохраните версию исходников/образов и защищённую копию прежнего env. Закройте входящий трафик на время обслуживания. Остановите все HTTP writers и фоновые процессы, включая внешние ERP-процессы. В HTTPS-установке добавляйте `-f compose.yaml -f compose.https.yaml` к командам для её сервисов.

   ```sh
   docker compose --env-file .env.docker --profile customer-email stop frontend backend notifications verification-emails
   umask 077
   mkdir -p backups
   docker compose --env-file .env.docker exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > backups/pre-accounts.dump
   docker compose --env-file .env.docker run --rm --no-deps --entrypoint tar backend -C /data/media -czf - . > backups/pre-accounts-media.tar.gz
   ```

   Если новый Compose уже требует отсутствующие ключи, остановите старые сервисы и сделайте backup через прежний Compose до замены файлов; либо сначала подготовьте новые ключи в env, сохранив старые значения БД. Проверьте восстановление dump и медиа на отдельной БД, а не только наличие файлов. Backup до `0004` содержит незашифрованные ПДн: храните его отдельно, с шифрованием и ограничением доступа.

2. Сгенерируйте **только отсутствующие** новые секреты локально, без отправки и публикации. Например, следующий вывод направляется в приватный файл, а не в общий журнал:

   ```sh
   umask 077
   python3 - <<'PY' > accounts-secrets.private
   import json, secrets
   print('PII_ENCRYPTION_KEYS=' + json.dumps({'v1': secrets.token_urlsafe(32)}, separators=(',', ':')))
   print('PII_ACTIVE_KEY_ID=v1')
   print('PII_INDEX_KEY=' + secrets.token_urlsafe(32))
   print('CHALLENGE_SECRET=' + secrets.token_urlsafe(48))
   PY
   ```

   Добавьте их в приватный `.env.docker`, не меняя пароль PostgreSQL, старые credentials и уже используемые ключи. `PII_ENCRYPTION_KEYS` — JSON map идентификатор→base64url AES-ключ из 32 случайных байт; `PII_INDEX_KEY` — другой независимый ключ из 32 байт; `CHALLENGE_SECRET` — независимый случайный секрет не короче 32 символов. Не копируйте сюда placeholder из примера. API и все workers должны получать одинаковые CRM-ключи. Сохраните обновлённый env отдельно до миграции.

3. При остановленных writers соберите кандидат и выполните явную миграцию:

   ```sh
   docker compose --env-file .env.docker build backend
   docker compose --env-file .env.docker run --rm --no-deps -e PII_MIGRATION_MAINTENANCE=true --entrypoint alembic backend upgrade head
   docker compose --env-file .env.docker run --rm --no-deps --entrypoint alembic backend current
   ```

   Ожидается revision `0006 (head)`. Не оставляйте `PII_MIGRATION_MAINTENANCE=true` в обычном env. Если найдены закрытые старые обращения с пустым resolution, миграция отказывает до backfill: исправьте данные осмысленным результатом по прежнему процессу и повторите из проверенного состояния. Не обходите проверку фиктивным текстом.

4. Запустите backend/frontend с прежней конфигурацией HTTPS; workers включайте только по их готовности. Проверки после выпуска: вход по подтверждённому email и возврат к исходной ссылке; admin видит пользователей и все операции; operator не видит администрирование; собственные записи не смешиваются; нет plaintext-ПДн в новых строках БД; каталог, медиа и гостевые повторы работают; новые номера обращений числовые, прежние квитанции сохранены. Регистрация и отправки остаются выключенными до отдельной настройки. После исторического перехода через `0004` нужен новый вход; переход `0005` → `0006` сам по себе сессии не отзывает.

Не используйте `docker compose down -v`: это удаляет базу и медиа. `0004` не поддерживает откат в plaintext. После новых записей нельзя просто вернуть старый образ/старый dump: старый код не читает шифрованную схему, а dump потеряет новые данные. При неудаче до открытия трафика восстановите проверенный комплект dump+медиа+прежний env+прежний образ в согласованном окне; после возобновления записей требуется отдельный план восстановления с сохранением новых данных.

## Сохранение и смена ключей

Backup БД после миграции бесполезен без соответствующих ключей; медиатом и env сохраняйте отдельными защищёнными копиями. При добавлении нового `PII_ACTIVE_KEY_ID` сохраните старые entries в `PII_ENCRYPTION_KEYS`: старые строки продолжают ссылаться на них. Смена активного ключа не перешифровывает существующие данные автоматически. Удалять ключ можно только после проверенной перешифровки всех зависимых строк и окончания хранения всех зависящих от него backup. Автоматической ротации нет. Не заменяйте `PII_INDEX_KEY`: lookup-индексы зависят от него и требуют отдельной согласованной перестройки. `CHALLENGE_SECRET` не заменяет ключи шифрования; его смена прерывает незавершённые проверки.

## Подключение SMTP без Telegram

Нужен выбранный SMTP-провайдер: разрешённый домен/адрес отправителя, включённая SMTP-аутентификация и отдельный пароль приложения/API SMTP credential по инструкции провайдера. Настройте записи подтверждения домена и SPF/DKIM/DMARC, если их требует провайдер. Обычный пароль почтового ящика не подставляйте, если провайдер выдаёт пароль приложения. Значения храните только в серверном env:

| Переменная | Значение |
| --- | --- |
| `SMTP_HOST` | Имя SMTP-сервера провайдера |
| `SMTP_PORT` | Обычно `465` для `tls`, `587` для `starttls`; сверить с провайдером |
| `SMTP_TLS_MODE` | `tls` (TLS с подключения) или `starttls` (обязательный STARTTLS) |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Отдельная пара credentials; оба заданы или оба пусты для разрешённого провайдером relay без SMTP AUTH |
| `SMTP_FROM` | Разрешённый отправитель вида `accounts@example.ru` |
| `CUSTOMER_REGISTRATION_ENABLED` | `false` до проверенной доставки, затем осознанно `true` |

TLS проверяет сертификат сервера системным trust store; режима без TLS/проверки сертификата нет. Backend и email-worker должны получать одинаковые SMTP-настройки. Worker запускается независимо от Telegram, только через профиль `customer-email`:

```sh
docker compose --env-file .env.docker --profile customer-email up -d --no-deps verification-emails
```

Сначала проверьте SMTP на отдельном тестовом окружении/почтовом ящике с разрешением на отправку. Затем при согласованном включении установите флаг и пересоздайте backend с его обычными Compose-файлами, не запуская Telegram-worker автоматически. Без SMTP signup/reset/profile activation возвращают безопасный `503`; наличие кнопки регистрации не означает, что письмо отправлено. Отключение signup не отключает вход уже активированных пользователей и восстановление при работающем SMTP. Код и исходный пароль не выдаются API/журналами; пароль хранится как Argon2-хэш, данные challenge и писем зашифрованы. Повторная регистрация занятого email не меняет существующий аккаунт. Код шестизначный, живёт 10 минут; повтор не раньше 60 секунд, максимум 5 неверных проверок. После восстановления пароля все прежние сессии отзываются.
