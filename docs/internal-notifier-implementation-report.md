Дата: 30.10.2026. Статус: реализовано, проверено, перенесено в рабочие каталоги. Продакшен этим этапом не обновлялся.

Последующее развёртывание на отдельном сервере и обновление CRM описаны в [production-отчёте](internal-notifier-production-report.md).

## Репозитории и состав

Соседний Git-репозиторий `/Users/mac/Documents/GIT/internal-notifier` создан и инициализирован на ветке main. В нём 25 файлов сервиса, тестов, контрактов, контейнеризации и документации. Коммиты и push не выполнялись.

Самостоятельный Python-пакет `internal_notifier` версии1.0.0 принимает уведомления по TLS/gRPC и доставляет Telegram Bot API. Из прямых runtime-зависимостей нужны только закреплённые grpcio/protobuf и стандартная библиотека; CRM, её PostgreSQL, модели, FastAPI и ключи ПДн сервису не нужны.

Основные файлы сервиса:

- `internal_notifier/server.py`: gRPC, проверка источника, ACL назначений и ссылок, один sender, управление процессом.
- `internal_notifier/notification_ledger.py`: самостоятельная долговечная SQLite-очередь, фиксация до ответа, повторы и квитанции.
- `internal_notifier/telegram_api.py`: ограниченный транспорт с проверяемым HTTPS к api.telegram.org и безопасными кодами ошибок.
- `internal_notifier/notification_protocol/`: V1 proto и SDK; исходный контракт/serialized descriptor и номера полей/enum сохранены.
- `Dockerfile`, `compose.yaml`, `config.example.json`, `README.md`: независимый запуск, TLS/config mounts, том очереди, статистика, backup/restore.

В MIRZAP67 оставлены существующие `NotifierClient`, TLS `RelayClient`, шифрованный PostgreSQL outbox и worker. Серверные `backend/app/telegram_relay.py`, `notification_ledger.py` и их тесты перенесены в отдельный репозиторий и удалены из CRM после проверки переноса. `compose.relay.yaml` и актуальный runbook теперь ссылаются на самостоятельный образ. Добавлены проверки V1-контракта и инструкции монтирования CA в API и worker.

Новые автоматические бизнес-события не добавлялись: отправляются существующие уведомления об обращениях. Поддержка безопасных ссылок на заказы/разделы/публикации/служебные страницы заложена в проверке сервиса; доступ по ссылке по-прежнему определяет приложение.

## Мок и develop-стенд

В `develop/` находятся:

- `telegram_mock.py`: настоящий локальный HTTP-сервер с ответами Bot API, capture сообщений, программируемыми429/ошибками/обрывом и ограничениями входа.
- `notifier_mock_launcher.py`: явная подстановка локального HTTP-транспорта через штатный parser отдельного сервиса. Production-транспорт не получил insecure/mock endpoint режима.
- `setup.py`: генерация отдельного исходного ключа, PII/session/DB ключей, fake bot/chat, TLS-сертификата с SAN notifier/localhost. Повторный запуск сохраняет существующие ключи и очередь.
- `compose.yaml`: пять самостоятельных сервисов postgres/backend/notifications/notifier/telegram-mock, сеть internal:true, собственная тестовая БД и тома, только loopback-порты.
- `smoke.py`: тест настоящей цепочки HTTP API → шифрованный outbox → TLS/gRPC → отдельный notifier/SQLite → fake HTTP Bot API.
- `tests/`, `README.md`: тесты и точные команды setup/up/down/smoke.

Мок никогда не пересылает сообщения наружу. Его HTTP-режим выбирает только develop-launcher. Контейнеры работают в закрытой внутренней сети; сборке образов нужен доступ к зависимостям. Предыдущие localhost8080, preview8081 и inbox8092 не менялись.

## Принятые решения и границы

1. Путь из сообщения прочитан как `../internal-notifier`; исходно каталога не было. Если имелось в виду другое имя, потребуется переименовать каталог и поправить build context.
2. Согласованный ранее gRPC/outbox дизайн сохранён; пользователь явно запросил реализацию. Повторное согласование архитектуры не запрашивалось; ошибочное толкование потребовало бы переработки интерфейсов.
3. Независимые задачи выполнялись параллельно с фиксированными интерфейсами и раздельным владением файлами. Стоимость неверного разделения — исправление интеграции; реальные Docker/E2E и итоговое ревью подтвердили стыки.
4. Переиспользована проверенная SQLite-очередь и текущие семантики доставки; новая шина/вторая БД/второй клиентский API не добавлялись. Сервис рассчитан на один экземпляр процесса/sender. Масштабирование потребует другого storage/ownership решения.
5. Сервисный ledger хранит служебный payload открытым текстом; диск и backup требуют соответствующей защиты. MIRZAP67 формирует уведомления без клиентских контактов/текста заявки; универсального детектора ПДн в произвольном тексте сервиса нет. CRM-outbox остаётся зашифрованным.
6. Повтор одного request_id защищён идемпотентностью сервиса; при неопределённом результате Bot API повторная доставка возможна и отражается UNCERTAIN/duplicate_possible. exactly-once/read acknowledgement не обещается.
7. Для теста выбран настоящий внешний gRPC-процесс и fake Bot API, без нового frontend. Это проверяет критический путь отправки; если нужен полноценный UI-стенд с рабочим HTTPS-origin CTA, это отдельное расширение.
8. Все исходные незакоммиченные изменения сохранены через baseline/hash guards и backup. Рабочие каталоги/артефакты не удалялись, потому что коммитов ещё нет; история этой работы доступна для проверки.

## Что остаётся перед реальным подключением

Подготовить хост с доступом к Telegram, TLS и приватную source/alias→bot/chat конфигурацию; проверить доступ CRM к gRPC и техническую доставку. Настройки клиента — существующие NOTIFICATION_TRANSPORT=relay, NOTIFICATION_RELAY_TARGET, NOTIFICATION_RELAY_TOKEN, NOTIFICATION_RELAY_CA_FILE и NOTIFICATION_DESTINATION_ALIAS. CA при необходимости монтируется readonly в API и worker; команды в runbook.

Перед включением рабочего notifications разобрать накопленный production backlog и сохранить ID/snapshots. После успешной проверки явно включить отправку и наблюдать квитанции. Старые live snapshots не перепривязывать и не делать автоматический relay→direct fallback.

Реальных Telegram/SMTP сообщений:0. Production SSH/deployment/изменений:0. Umami/аналитика и новые бизнес-триггеры не входят в этот этап.
