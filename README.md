# MIRZAP67 · витрина автозапчастей и CRM

Тонкий frontend на Vue 3 + Vite: лендинг с категориями и акциями/объявлениями, каталог, поиск по артикулу, корзина, оформление без оплаты и CRM с заказами, обращениями, категориями и редактором контента сайта. Рабочий backend на FastAPI хранит данные в PostgreSQL и изображения на постоянном томе. Полная сборка запускается в Docker; отдельный браузерный деморежим сохраняет данные локально, а обращения — только в памяти вкладки. Конфигурация 1С пока неизвестна: адаптер обмена ещё не подключён.

## Импорт номенклатуры

Администратору доступен импорт PDF с предварительной сверкой цен и физических остатков, назначением единиц и обработкой неоднозначных строк. Дробные количества поддерживаются в каталоге, корзине и заказах. Для будущей учётной системы подготовлен адаптер, использующий тот же механизм сверки; реальный обмен пока не подключён. Подробности и запуск worker: [Импорт номенклатуры](docs/catalog-import.md).

## Запуск

Для разработки frontend нужен Node.js 22.12 или новее. Для запуска всей системы используйте Docker ниже.

```sh
npm ci
npm run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Vite слушает только локальный интерфейс. Другой порт: `npm run dev -- --port 5174`.

`npm run dev` и `npm run build` используют API на том же origin по пути `/api`. Dev-сервер Vite проксирует `/api` в `http://127.0.0.1:8000`; адрес меняется через `API_PROXY_TARGET` из `.env` (пример — [.env.example](.env.example)). Эта переменная нужна только dev-прокси и не попадает в frontend bundle. `VITE_API_BASE_URL` задаёт путь API на том же origin, по умолчанию `/api`. `VITE_DATA_MODE=api` или `demo` — необязательное явное переопределение источника, имеющее приоритет над режимом команды.

Без backend приложение показывает ошибки загрузки и кнопки повтора. Сетевой сбой или некорректный ответ API не переключают его на демокаталог и не создают локальный успешный заказ.

Production сборка: `npm run build`; локальный просмотр результата: `npm run preview` (порт 4173). Для размещения используйте `dist/` и серверную маршрутизацию `/api` к backend: preview и static hosting не заменяют dev-прокси.

Демо без backend:

```sh
npm run dev:demo
```

Для сборки демо используйте `npm run build:demo`, затем `npm run preview`. Обе сборки записываются в `dist/`; выбирайте нужный режим перед preview. Если задан `VITE_DATA_MODE`, проверьте его значение.

## Запуск в Docker и перенос на другое устройство

На устройстве нужен Docker с Compose 2.17 или новее; устанавливать Node.js и Python отдельно не требуется. Из каталога проекта запустите:

```sh
./scripts/start.sh
```

При первом запуске скрипт создаёт `.env.docker` и останавливается: укажите в `ADMIN_LOGIN` действующий email администратора и повторите команду. Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080), редактор — [CRM → Контент сайта](http://127.0.0.1:8080/#crm-content). Вход администратора: email из `ADMIN_LOGIN`, уникальный пароль — из `ADMIN_PASSWORD` того же закрытого файла.

Скрипт создаёт `.env.docker` со случайными паролями PostgreSQL, администратора, ключом сессий и независимыми ключами шифрования/поиска ПДн и email-подтверждения, с правами `0600`. Существующий файл сохраняется и не дополняется. Для обновления существующей базы сначала выполните [подготовку backup, ключей и миграции 0004/0005 в окно обслуживания](docs/accounts-release.md); обычный старт применяет миграции автоматически. [.env.docker.example](.env.docker.example) описывает параметры; пустые секреты из примера не позволяют запустить систему. Первый запуск новой базы применяет миграции Alembic, создаёт администратора и пример каталога. Изменения затем хранятся на сервере и доступны с другого браузера.

После создания администратора изменение `ADMIN_LOGIN`/`ADMIN_PASSWORD` в окружении не переименовывает его и не сбрасывает пароль. Отдельного оператора можно создать с явно указанным email, введя пароль в скрытом приглашении. Это доверенное серверное создание сотрудника с подтверждённым email; письмо не отправляется:

```sh
docker compose --env-file .env.docker exec backend python -m app.manage_staff operator@example.com --name 'Менеджер'
```

Основной Compose запускает четыре сервиса; независимый пятый `verification-emails` включается только профилем `customer-email` после настройки SMTP:

| Сервис | Образ | Назначение |
|---|---|---|
| `frontend` | `lavr-crm:api` | Vue и Nginx, внешний порт 8080 |
| `backend` | `lavr-crm-backend:local` | FastAPI, авторизация, каталог, заказы, обращения и контент |
| `notifications` | `lavr-crm-backend:local` | Отдельный процесс отправки Telegram из PostgreSQL outbox |
| `postgres` | `postgres:17-alpine` | Постоянная база данных |
| `verification-emails` (опционально) | `lavr-crm-backend:local` | Подтверждение email и восстановление пароля; профиль `customer-email` |

Frontend обращается к `/api` на origin сайта; Nginx пересылает запросы в `backend:8000`. Backend и PostgreSQL не публикуют порты на устройство. Backend и notifications работают под UID 1000; служебные проверки готовности учитывают доступность БД и API. Compose ждёт PostgreSQL, затем backend с миграциями, затем frontend и notifications. У notifications отключена HTTP-проверка здоровья: процесс не поднимает HTTP-сервер. При штатном обновлении backend через Compose frontend и notifications перезапускаются. [Порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/).

`postgres_data` хранит PostgreSQL, `media_data` — изображения. Обычная остановка и пересоздание контейнеров сохраняют оба тома:

```sh
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs -f backend
docker compose --env-file .env.docker down
./scripts/start.sh
```

`docker compose down -v` удаляет тома и данные. Не используйте `-v` для обычной остановки. Сохраните `.env.docker` отдельно: его нельзя перегенерировать для существующей PostgreSQL, потому что пароль БД задаётся при её первой инициализации, а потеря ключей ПДн делает зашифрованные данные нечитаемыми. Старые ключи нужны также для восстановления backup. Файл исключён из Git и Docker build context; секреты и рабочие данные не входят в образы.

Локальные значения: `APP_BIND=127.0.0.1`, `APP_PORT=8080`, `COOKIE_SECURE=false`, `SEED_DEMO_CATALOG=true`. Для другого порта измените также порт в `ALLOWED_ORIGINS`. Для серверного размещения настройте внешний HTTPS-прокси, публичный адрес в `ALLOWED_ORIGINS`, `COOKIE_SECURE=true` и `SEED_DEMO_CATALOG=false`; `APP_BIND=0.0.0.0` открывает сайт по сети. UUID и SHA-256 в браузере требуют HTTPS либо localhost, поэтому сетевой HTTP не заменяет серверное размещение. Перезапустите сборку после изменения параметров. Отключение начального каталога не удаляет уже созданные товары.

Для HTTPS через Docker предусмотрен [compose.https.yaml](compose.https.yaml) с Caddy. До первого запуска новой базы подготовьте `.env.docker` с отдельными серверными секретами и `SEED_DEMO_CATALOG=false`: обычный `scripts/start.sh` создаёт файл с демонстрационным наполнением и сразу запускает систему. Задайте `PUBLIC_SITE_URL=https://ваш-домен`, такой же origin в `ALLOWED_ORIGINS`, `COOKIE_SECURE=true`; сохраните `APP_BIND=127.0.0.1` и `TELEGRAM_NOTIFICATIONS_ENABLED=false`. DNS домена должен указывать на сервер, входящие TCP-порты 80/443 — быть доступны. Выполните:

```sh
docker compose --env-file .env.docker stop notifications
docker compose --env-file .env.docker -f compose.yaml -f compose.https.yaml up -d --build --wait backend frontend https
```

Эту же команду с обоими Compose-файлами используйте для обновлений HTTPS-установки. Она не запускает процесс notifications. Caddy получает и продлевает сертификат автоматически, перенаправляет HTTP на HTTPS и хранит сертификаты в постоянных томах `caddy_data`/`caddy_config`. API направляется непосредственно в backend с проверенным IP посетителя для лимита обращений; backend доверяет только настроенной сети прокси. При изменении Docker-сети проверьте `TRUSTED_PROXY_HOSTS`. Для просмотра журнала: `docker compose --env-file .env.docker -f compose.yaml -f compose.https.yaml logs --tail=100 https`. Публичный HTTPS не устраняет отдельные ограничения обмена с 1С и исходящего доступа к Telegram.

Отдельный сервер находится в соседнем репозитории `../internal-notifier`; [Compose и runbook переключения direct → relay](docs/telegram-relay-runbook.md) используют его самостоятельный образ `internal-notifier:local`. Сервис не получает CRM-БД и ключи ПДн. На VM `157.228.139.156` Telegram egress заблокирован; нужен другой доступный хост. До согласованного подключения держите отправку выключенной.

Прямой Telegram (`NOTIFICATION_TRANSPORT=direct`, по умолчанию) настраивается только на сервере в `.env.docker`: `TELEGRAM_BOT_TOKEN` — токен бота, `TELEGRAM_CHAT_ID` — канал команды, где бот может публиковать, `PUBLIC_SITE_URL` — доступный сотрудникам origin сайта (`https://example.ru`, без пути, query и fragment). Сначала оставьте `TELEGRAM_NOTIFICATIONS_ENABLED=false`, проверьте подключение командой `docker compose --env-file .env.docker run --rm --no-deps backend python -m app.telegram_cli check`, затем явно отправьте одно техническое сообщение той же командой с `test` вместо `check`. Без `PUBLIC_SITE_URL` тест проверяет доставку только текста; для кнопки CRM и автоматических уведомлений задайте адрес. [Пошаговое подключение своего канала, получение его ID и включение очереди](docs/telegram-integration-design.md#подключение-своего-тестового-канала). После отдельного включения `TELEGRAM_NOTIFICATIONS_ENABLED=true` и `./scripts/start.sh` worker отправит также накопленные уведомления старых обращений. Ссылка строится из `PUBLIC_SITE_URL`, не из входного Host; для проверки с телефона нужен доступный HTTPS-адрес, `127.0.0.1` откроет сам телефон. Эти параметры не являются `VITE_*` и не попадают в браузер.

`TRUSTED_PROXY_HOSTS` задаёт через запятую адреса/CIDR доверенных прокси для `X-Real-IP` и лимита публичной формы; в Compose по умолчанию `172.16.0.0/12`, при смене сети укажите фактическую доверенную сеть или адрес прокси. Произвольный `X-Forwarded-For` не учитывается. После изменения выполните `./scripts/start.sh`; состояние отправки видно через `docker compose --env-file .env.docker logs -f notifications`.

Пустые настройки Telegram и выключенная отправка не мешают приёму и работе с обращениями: они сохраняются, а события уведомлений ждут включения. Notifications обрабатывает только `feedback_telegram`, не события 1С. Отправка и ошибки не блокируют CRM; повторы и общая пауза после `429` хранятся в БД. При неоднозначном сетевом сбое возможен повтор Telegram-сообщения с тем же номером обращения. Токен, полные контакты и текст обращения в уведомление и журналы не входят.

`APP_MODE=api` — рабочий режим по умолчанию. `APP_MODE=demo` выбирает прежний браузерный демонстрационный источник при сборке; его данные остаются в конкретном браузере и не попадают в серверные тома. После изменения режима запускайте скрипт без `--no-build`.

Перенос из исходников: скопируйте проект на новое устройство и запустите `./scripts/start.sh`. Не нужны `node_modules`, `dist`, старые `.env` и Python на принимающем устройстве. Docker соберёт образы для его архитектуры; для ARM используйте этот способ.

Для запуска готовых образов нужен архив из той же версии проекта, что и `compose.yaml`. Прежний `artifacts/docker/lavr-crm-full-stack-amd64.tar` не обновлён для обращений и нового процесса notifications; для текущей версии используйте сборку из исходников выше либо сначала экспортируйте актуальные образы.

Для переноса актуального архива скопируйте его, `compose.yaml` и `scripts/start.sh`, сохраняя каталог `scripts`. На устройстве AMD64 с Docker выполните из каталога с Compose:

```sh
docker load -i lavr-crm-full-stack-amd64.tar
sh scripts/start.sh --no-build
```

Архив включает frontend, backend и PostgreSQL; notifications использует тот же backend-образ. `--no-build` не собирает и не скачивает образы; новая `.env.docker` создаётся из загруженного backend-образа. Исходники `backend/` для этого запуска не нужны. Архив AMD64 не превращается в ARM64; на ARM нужна сборка из исходников. Новый сервер получает новую базу; существующие данные переносятся отдельно с резервной копией и прежними секретами.

Для согласованной резервной копии временно остановите frontend, backend и notifications, оставив PostgreSQL работающим:

```sh
umask 077
mkdir -p backups
docker compose --env-file .env.docker --profile customer-email stop frontend backend notifications verification-emails
docker compose --env-file .env.docker exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > backups/postgres.dump
docker compose --env-file .env.docker run --rm --no-deps --entrypoint tar backend -C /data/media -czf - . > backups/media.tar.gz
docker compose --env-file .env.docker start backend notifications frontend
```

Если email-worker ранее работал, запустите его отдельно через профиль `customer-email` после backup. Сохраните оба файла и `.env.docker` со всеми действующими ключами ПДн в защищённом хранилище. Копия содержит контакты заказов и обращений, заметки, очередь уведомлений и приватные изображения; Docker-архив их не заменяет. Восстановление БД выполняется через `pg_restore`, файлы возвращаются в `media_data` с владельцем UID 1000 перед запуском backend.

## Аккаунты покупателей

В шапке доступны «Войти» и «Зарегистрироваться», после входа — личный кабинет с собственными заказами/обращениями. Регистрация требует телефон, email и выбранный пароль с подтверждением кодом из письма; телефон пока не подтверждается. Гостевые документы автоматически к аккаунту не привязываются. SMTP пока не настроен в production, `CUSTOMER_REGISTRATION_ENABLED=false`; доставка писем включается независимо от Telegram через `customer-email`. [Права, миграция данных, сохранение ключей и настройка SMTP](docs/accounts-release.md). Демо явно имитирует аккаунты и не отправляет реальные письма.

## Прямые ссылки

Разделы и карточки можно открывать по адресам: `/#catalog?category=filters`, `/#catalog?product=<ID>`, `/#crm?order=<ID>`, `/#crm-feedback?case=<ID>`, `/#account-orders?order=<ID>`, `/#account-feedback?case=<ID>`, `/#admin-users?user=<ID>`, `/#crm-content?tab=media` и `/#crm-content?tab=publications&publication=<ID>`. Для публичных материалов доступны `/#home?section=offers` и `/#home?publication=<ID>`. Перезагрузка, новая вкладка и история браузера сохраняют назначение; закрытие карточки возвращает к списку или её безопасному исходному разделу.

При переходе через вход назначение сохраняется в проверенном внутреннем `returnTo`; при необходимости завершить профиль оно сохраняется до подтверждения email. Ссылка не предоставляет права: служебные страницы требуют operator/admin, редактирование сайта/пользователей — admin, личные карточки доступны владельцу. Гостевые заявки открываются сотруднику через CRM и не присваиваются аккаунту по совпавшим контактам. Поля форм, контакты, пароли и токены в адрес не записываются. [Карта маршрутов и правила доступа](docs/superpowers/specs/2026-10-29-direct-links-design.md).

## Граница internal-notifier

В приложении подготовлен типизированный интерфейс `NotifierClient.submit/get/close`, существующий gRPC/TLS-клиент и builder безопасных ссылок. Wire-контракт `notifications.v1.NotificationRelay`, encrypted outbox и сохранённые snapshots остаются совместимыми. `NOTIFICATION_TRANSPORT` принимает только `direct` или `relay`; неизвестный режим отклоняется до отправки.

Сервер `internal-notifier` вынесен в отдельный репозиторий `../internal-notifier` со своим образом, SQLite ledger и тестами. В CRM остаются только SDK, protobuf V1 и outbox worker; серверные модули из backend удалены. Внешний сервис проверяет per-source ACL и ссылки navigation-v1. Уведомления о заказах используют событие `order_telegram`; режим `--orders-only` обрабатывает только их. Изолированный стек `develop/` проверяет настоящий HTTP API → outbox → TLS gRPC → standalone ledger → локальный fake Bot API на синтетических данных, без реальных отправок Telegram; команды находятся в [develop/README.md](develop/README.md). [Контракт и порядок переключения](docs/superpowers/specs/2026-10-29-internal-notifier-transition-design.md), [варианты аналитики и объяснение Umami](docs/visitor-analytics-options.md).

## Работа через API

Оформление покупателя сейчас доступно как самовывоз без онлайн-предоплаты,
с оплатой в магазине. [Два сценария оформления](docs/checkout-flows.md) разделяют
текущую форму и будущую оплату через банк. Новые запросы доставки от покупателя
не принимаются; сохраненная история и повтор прежней квитанции остаются доступны.

Главная, категории, товары, заказы и обращения загружаются асинхронно. Поиск, фильтры, сортировка и пагинация передаются серверу. Ответы HTTP проверяются перед использованием. Единая сессия возвращает профиль и capabilities без назначенной роли/активности. Новый подтверждённый пользователь — `partner` с доступом только к собственным записям; `operator` работает с заказами, обращениями и операционным обменом; `admin` имеет полный доступ, включая возможности оператора, сайт и пользователей. Роли и активность доступны только в admin users API и на [странице пользователей](http://127.0.0.1:8080/#admin-users). Закрытые изменения передают CSRF-токен, изменения существующих заказов, обращений, категории товара, настроек сайта и публикаций — `If-Match`.

Адаптер конкретной 1С ещё не подключён. API принимает заказ без онлайн-оплаты в CRM: `new/not_connected`, локальный резерв и `order_telegram` записываются атомарно. Менеджер подтверждает заказ, готовит к выдаче, завершает или отменяет; отмена освобождает резерв, завершение списывает остаток. Проверки актуальных цен, единиц, остатков и видимости сохраняются. При настроенном адаптере действует прежний путь `pending_sync/order_export`; ручные заказы автоматически в него не переводятся. [Сценарий, проверки и запуск Telegram](docs/manual-orders.md).

В API-режиме в `localStorage` frontend записывает только черновик корзины `[{ productId, quantity }]` под ключом `lavr.cart.v1`. В `sessionStorage` хранится технический ключ попытки оформления `lavr.checkout-attempt.v1`: UUID и SHA-256 отпечаток запроса, без тела заказа и контактов. Для обращения используются отдельные ключи `lavr.feedback-attempt.v1:submission` и `lavr.feedback-attempt.v1:order:<ID>`, также только UUID и SHA-256. Они позволяют повторить запрос с тем же ключом после обновления страницы и повторного ввода формы. Контакты и тексты обращений, формы, загруженные данные и клиентское состояние сессии находятся в памяти страницы; персональные данные в browser storage не записываются. Цена и итог в корзине предварительные; окончательную цену и допустимость заказа обязан проверить backend. При ошибке оформления форма и корзина сохраняются, успех отображается только после проверенного ответа API.

В каталоге администратора подключены создание категории и назначение категории существующему товару. Создание учётной номенклатуры доступно только в демо до согласования записи в неизвестную конфигурацию 1С.

В [CRM → Контент сайта](http://127.0.0.1:5173/#crm-content) администратору доступны три вкладки:

- «Главная и меню»: тексты и изображение первого экрана, кнопка и внутренняя цель, контакты магазина, заголовки разделов, подписи, порядок и видимость пунктов меню.
- «Публикации»: акции, объявления и горячие предложения, текст, до восьми изображений, внутренняя ссылка, порядок, статусы «Черновик»/«Опубликовано»/«В архиве» и необязательный период показа. Даты вводятся по часовому поясу устройства; черновики, архив и записи вне срока не показываются на витрине.
- «Изображения»: загрузка JPG/PNG/WebP до 5 МиБ и 4096×4096 с альтернативным текстом, библиотека с пагинацией. HTTP-клиент отправляет поля `file` и `alt` через multipart; настройки и публикации сохраняют ID медиа, а пути предпросмотра и публичных файлов возвращает API.

Редактор сохраняет существующий дизайн лендинга и обычный текст без HTML. При ошибке изменения остаются в форме; конфликт `412` требует загрузить актуальную версию, уход с несохранёнными изменениями запрашивает подтверждение. FastAPI проверяет роль, Origin и CSRF, версии и содержимое изменений. Изображение доступно публично только при актуальной ссылке с витрины, опубликованного материала или видимого товара; черновики и архив остаются закрытыми. Конструктор страниц и расчёт скидок не входят в редактор.

## Обращения покупателей

На главной в блоке помощи и в контактах подвала доступны «Свяжитесь со мной» и «Оставить запрос». Вход посетителя не требуется. Укажите телефон, email или пару «сервис + контакт» мессенджера; можно несколько контактов, каждый проверяется. Имя необязательно, для запроса обязателен текст до 2000 символов. Принятая форма получает номер только после сохранения в PostgreSQL; повтор той же попытки возвращает ту же публичную квитанцию без данных CRM.

Публичное подтверждение не показывает номер обращения. «Отправить ещё обращение» открывает чистую форму; после закрытия и нового открытия также можно отправить следующую заявку без ожидания. После ошибки введённые данные и ключ повтора сохраняются. Серверная защита от частых отправок продолжает действовать.

После запуска Docker откройте [CRM → Обращения](http://127.0.0.1:8080/#crm-feedback) и войдите как operator/admin. Для Vite адрес — [http://127.0.0.1:5173/#crm-feedback](http://127.0.0.1:5173/#crm-feedback). В списке есть фильтр статуса, поиск по номеру/полному нормализованному телефону или email и пагинация. Карточка открывается напрямую по `/#crm-feedback?case=<UUID>`; ссылка сохраняется через вход и истечение сессии. Telegram содержит номер, московское время, тип формы и кнопку на эту защищённую карточку; сама ссылка доступа не даёт.

«Взять в работу» переводит `new` → `in_progress` и назначает текущего сотрудника. Читать могут все менеджеры; заметки, закрытие и создание заказа у назначенного обращения доступны ответственному либо admin. Заметка может указывать способ связи. Закрыть можно новое или взятое обращение, обязательно указав результат. `closed` и `converted` — конечные статусы; `converted` устанавливает только успешное создание заказа. Изменения проверяют Origin, CSRF и `If-Match`: старая версия даёт `412`, запрещённый переход — `409`, чужой владелец — `403`. Телефон и email доступны для звонка/письма; контакт мессенджера отображается текстом для копирования, автоматической переписки с клиентом нет.

В обращении в работе нажмите «Подготовить заказ», выберите товары, количества и получение; при доставке нужен адрес. Контакты подставляются из обращения, но для заказа требуются реальные имя и российский телефон, даже если посетитель оставил только email/мессенджер. Подготовка использует отдельную форму и не меняет покупательскую корзину. Заказ, резерв, событие `order_telegram`, при подключенной 1С также `order_export`, связь, статус и аудит записываются одной транзакцией. Повтор с тем же ключом возвращает исходную карточку конверсии до проверки устаревшей версии и ERP; новое тело с тем же ключом даёт `409`, второй заказ из обращения не создаётся. После успеха «Открыть заказ» ведёт на `/#crm?order=<UUID>`. Без подключённой 1С создаётся ручной заказ; при ошибке цены, остатка или других проверок обращение остаётся в работе, введённая форма сохраняется. Приём, заметки и закрытие от 1С не зависят.

В `npm run dev:demo` используйте вымышленные контакты: обращения и заметки живут только в памяти текущей вкладки и исчезают при перезагрузке. Уведомления демонстрационные. Конверсия создаёт обычный демозаказ в существующем `sessionStorage` `lavr.orders.v1`; такой заказ сохраняется при перезагрузке, связь с исчезнувшим демообращением — нет.

## Мобильное отображение

Витрина и CRM используют те же Vue-компоненты и API на телефоне, планшете и компьютере. Отдельная мобильная база или backend не нужны. Меню, категории и публикации по-прежнему приходят с сервера; адаптация меняет только отображение.

До 1100 px пункты меню доступны через раскрываемое «Меню», до 760 px поиск переносится на отдельную строку, фильтры — над товарами, корзина и формы — в одну колонку. Основные кнопки и области нажатия на телефоне имеют размер от 44 px; поля ввода и select — шрифт 16 px. Масштабирование страницы разрешено. Таблицы CRM прокручиваются внутри подписанной области, с подсказкой для узкого экрана; остальная страница не требует горизонтальной прокрутки. Кнопка закрытия карточки остаётся доступна при прокрутке диалога.

Приёмка включает мобильные касания на 320×740, 390×844 и 844×390, поиск по артикулу → корзина → заказ, работу с категориями, серверное меню и вход сотрудника. Эмуляция Chrome не заменяет проверку клавиатуры и масштабирования на настоящих iPhone/Android.

## Что проверить в демо

1. Найдите `W 914/2`, `Bosch фильтр` или `BKR6E-11`; попробуйте категорию, бренд, наличие и сортировку цены.
2. Добавьте товар, перейдите в корзину, измените количество. Больше демонстрационного остатка добавить нельзя.
3. Введите вымышленные имя и телефон, например `Демо Покупатель`, `+7 (999) 123-45-67`. Для доставки укажите тестовый адрес.
4. Нажмите «Создать демозаказ». Контакты и состав появятся в CRM текущей вкладки.
5. Откройте карточку заказа и последовательно измените статус: новый → подтверждён → готов к выдаче → завершён. Отмена возможна до завершения; финальные статусы не меняются.
6. Вернитесь в каталог и оформите второй демозаказ. Заказы текущей вкладки сохраняются при обновлении страницы.

В [CRM → Каталог](http://127.0.0.1:5173/#crm-catalog) создайте категорию, затем добавьте номенклатуру: название, артикул, бренд, категория, цена в рублях и остаток. Название категории уникально; одинаковый артикул одного бренда добавить повторно нельзя. Категорию существующего товара можно изменить в таблице. Новый товар сразу доступен на главной, в поиске и корзине; после обновления страницы он сохраняется. Основной поиск — по артикулу, дополнительно поддержаны название, бренд и внутренний/внешний ID.

Главная начинается с трёх примеров акций и объявлений из `src/data/demo-site.js`. В [CRM → Контент сайта](http://127.0.0.1:5173/#crm-content) измените заголовок и меню, загрузите изображение, создайте черновик, затем опубликуйте или архивируйте его. После сохранения витрина обновляется; проверьте результат и после перезагрузки страницы. Публикация рекламной акции не меняет цену товара или заказа.

## Ограничения демо

Цены, остатки, артикулы, описания и изображения демонстрационные; совместимость запчастей не проверяется. Источники и лицензии фото находятся в [docs/assets.md](docs/assets.md) и доступны через ссылку в футере сайта.

Корзина хранится в `localStorage` с ключом `lavr.cart.v1` (только `productId` и `quantity`). Только в demo-режиме заказы с контактами, включая созданные из обращений, сохраняются в `sessionStorage`, ключ `lavr.orders.v1`, в текущей вкладке; восстановление вкладки браузером может восстановить и сессию. Сами демообращения не записываются в хранилище браузера и исчезают при перезагрузке. Используйте вымышленные контакты. Для явного удаления демоданных очистите хранилище этого сайта в настройках браузера.

Категории и номенклатура сохраняются в `localStorage`, ключ `lavr.catalog.v1`, и обновляются между вкладками этого браузера. Ошибка записи не очищает формы и не применяет изменение. Если сохранённый каталог повреждён или недоступен, UI показывает исходный демокаталог и блокирует изменения/оформление, сохраняя прежние данные. После восстановления корректного каталога работа возобновляется. Это локальное демо без совместного редактирования несколькими менеджерами; одновременные записи из вкладок используют последнюю сохранённую версию.

Настройки сайта и публикации сохраняются JSON-снимком в `localStorage` под ключом `lavr.site.v1`; загруженные файлы — как Blob в IndexedDB `lavr-media-v1`. В JSON хранятся ID изображений; временные `blob:`-адреса создаются заново при чтении файлов. Ошибки записи сохраняют форму и прежние данные, повреждённый JSON переводит редактор в режим чтения. Версии записей обнаруживают устаревшее сохранение, но демо не заменяет серверные транзакции или общую медиабиблиотеку. Очистка хранилища сайта удаляет эти изменения и файлы.

Демозаказы не отправляются магазину или в 1С, CRM в демо открыта. Это режим согласования интерфейса с вымышленными данными. В API-режиме работают серверная авторизация, PostgreSQL, общий каталог, заказы и медиабиблиотека. Реальный обмен с 1С ещё предстоит: неизвестна конфигурация и доступ к базе заказчика.

Для рабочей CRM и витрины MVP подтверждён Vue 3 + Vite. SEO отложено до следующих этапов; необходимость Nuxt будет оцениваться после MVP.

## Проверки

```sh
npm test
npm run check
npm run build
npm run build:demo
```

Тесты используют встроенный `node:test`: домен демо, источники данных, проверка HTTP-ответов, схемы контента и медиа, сохранение публикаций и версий, черновик корзины и действия со статусами. Сборки проверяют компиляцию Vue templates и выбор источника.

Для интеграционной проверки Docker нужны оба собранных образа и Node.js на машине проверки:

```sh
APP_MODE=demo docker compose --env-file .env.docker build frontend
APP_MODE=api docker compose --env-file .env.docker build frontend
node --test tests/docker-smoke.mjs
```

Сценарии запускают временные контейнеры и HTTP-сервер проверки, затем удаляют их. Проверяются выбор источника, пользователь без root, healthcheck, HTML/assets и 404, передача API-пути/заголовков/cookie, multipart 5 МиБ и отказ для тела больше лимита Nginx. Проверка proxy использует HTTP-сервер теста, а не реализованный FastAPI.

Дополнительная браузерная проверка требует установленный Google Chrome и временный Playwright. На macOS/Linux его можно установить вне проекта:

```sh
npm install --prefix /tmp/lavr-browser-qa playwright
```

Демо-сценарии `tests/browser-smoke.mjs` ожидают `http://127.0.0.1:5173`. Запустите `npm run dev:demo` либо соберите демо и в отдельном терминале откройте preview на этом порту:

```sh
npm run build:demo
npm run preview -- --port 5173 --strictPort
```

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/browser-smoke.mjs
```

Скрипт проверяет заказ, каталог, редактор контента, сохранение загруженных файлов после перезагрузки, обмен вкладок, ошибки хранилища, клавиатуру, мобильные касания и размеры элементов; перезаписывает скриншоты в `docs/previews` тестовыми данными.

`tests/browser-api.mjs` проверяет production API-сборку с перехваченными HTTP-ответами. Перед ним соберите `npm run build` и запустите preview на том же порту 5173:

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/browser-api.mjs
```

Это проверка клиента на HTTP-заглушке. Реальный FastAPI/PostgreSQL проверяются отдельно backend-тестами и сквозным сценарием полной Docker-сборки.

Новые сценарии личного кабинета и прямых ссылок запускаются на той же API-сборке с явным адресом (ответы API перехватываются тестом):

```sh
BROWSER_BASE_URL=http://127.0.0.1:5173 PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/browser-accounts.mjs tests/browser-routes.mjs tests/browser-private-routes.mjs
```

Проверяются возврат после входа/завершения профиля, ссылки и история modal, новая вкладка, CMS-подменю/карточки вне страницы списка, ограничения ролей и поздние ответы после смены страницы.

Для backend-тестов нужен Python 3.13 и отдельная тестовая PostgreSQL с именем базы, заканчивающимся на `_test`. Задайте `TEST_DATABASE_URL` для неё; каждый тест создаёт и удаляет изолированную схему, рабочую БД указывать нельзя.

```sh
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
cd ..
```

После `./scripts/start.sh` сквозной сценарий проверяет настоящий Nginx, FastAPI, PostgreSQL и изображения на компьютере и мобильном экране, без перехвата HTTP-ответов:

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/full-stack.mjs
```

Он читает пароль администратора из локальной `.env.docker`, создаёт служебные материалы, возвращает исходный баннер и оформление товара, архивирует проверочную публикацию и скрывает проверочную категорию. Проверка выполняется на тестовой установке; запись аудита и загруженный проверочный файл остаются в её серверных данных. Другой адрес задаётся через `BASE_URL`, другой файл окружения — через `DOCKER_ENV_FILE`.
