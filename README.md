# LAVR · витрина автозапчастей и CRM

Тонкий frontend на Vue 3 + Vite: лендинг с категориями и акциями/объявлениями, каталог, поиск по артикулу, корзина, оформление без оплаты и CRM с заказами, категориями и редактором контента сайта. Рабочий backend на FastAPI хранит данные в PostgreSQL и изображения на постоянном томе. Полная сборка запускается в Docker; отдельный браузерный деморежим сохраняет данные локально. Конфигурация 1С пока неизвестна: адаптер обмена ещё не подключён.

## Запуск

Для разработки frontend нужен Node.js 22.12 или новее. Для запуска всей системы используйте Docker ниже.

```sh
npm ci
npm run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Vite слушает только локальный интерфейс. Другой порт: `npm run dev -- --port 5174`.

`npm run dev` и `npm run build` используют API на том же origin по пути `/api`. Dev-сервер Vite проксирует `/api` в `http://127.0.0.1:8000`; адрес меняется через `API_PROXY_TARGET` из `.env` (пример — [.env.example](.env.example)). Эта переменная нужна только dev-прокси и не попадает в frontend bundle. `VITE_API_BASE_URL` задаёт путь API на том же origin, по умолчанию `/api`. `VITE_DATA_MODE=api` или `demo` — необязательное явное переопределение источника, имеющее приоритет над режимом команды.

Без backend приложение показывает ошибки загрузки и кнопки повтора. Сетевой сбой или некорректный ответ API не переключают его на демокаталог и не создают локальный успешный заказ.

Production сборка: `npm run build`; локальный просмотр результата: `npm run preview` (порт 4173). Для размещения используйте `dist/` и серверную маршрутизацию `/api` к backend: preview и static hosting не заменяют dev-прокси.

Демо без backend:

```sh
npm run dev:demo
```

Для сборки демо используйте `npm run build:demo`, затем `npm run preview`. Обе сборки записываются в `dist/`; выбирайте нужный режим перед preview. Если задан `VITE_DATA_MODE`, проверьте его значение.

## Запуск в Docker и перенос на другое устройство

На устройстве нужен Docker с Compose v2 или новее; устанавливать Node.js отдельно не требуется. Из каталога проекта запустите:

```sh
./scripts/start.sh
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080), редактор — [CRM → Контент сайта](http://127.0.0.1:8080/#crm-content). Вход администратора: логин `admin`, уникальный пароль находится в локальном `.env.docker` в поле `ADMIN_PASSWORD`.

Скрипт создаёт `.env.docker` с случайными паролями PostgreSQL, администратора и ключом сессий, с правами `0600`. Существующий файл сохраняется. [.env.docker.example](.env.docker.example) описывает параметры; пустые секреты из примера не позволяют запустить систему. Первый запуск новой базы применяет миграции Alembic, создаёт администратора и пример каталога. Изменения затем хранятся на сервере и доступны с другого браузера.

Compose запускает три сервиса:

| Сервис | Образ | Назначение |
|---|---|---|
| `frontend` | `lavr-crm:api` | Vue и Nginx, внешний порт 8080 |
| `backend` | `lavr-crm-backend:local` | FastAPI, авторизация, каталог, заказы и контент |
| `postgres` | `postgres:17-alpine` | Постоянная база данных |

Frontend обращается к `/api` на origin сайта; Nginx пересылает запросы в `backend:8000`. Backend и PostgreSQL не публикуют порты на устройство. Backend работает под UID 1000; служебные проверки готовности учитывают доступность БД и API. Compose ждёт PostgreSQL, затем backend, затем frontend. [Порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/).

`postgres_data` хранит PostgreSQL, `media_data` — изображения. Обычная остановка и пересоздание контейнеров сохраняют оба тома:

```sh
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs -f backend
docker compose --env-file .env.docker down
./scripts/start.sh
```

`docker compose down -v` удаляет тома и данные. Не используйте `-v` для обычной остановки. Сохраните `.env.docker` отдельно: его нельзя перегенерировать для существующей PostgreSQL, потому что пароль БД задаётся при её первой инициализации. Файл исключён из Git и Docker build context; секреты и рабочие данные не входят в образы.

Локальные значения: `APP_BIND=127.0.0.1`, `APP_PORT=8080`, `COOKIE_SECURE=false`, `SEED_DEMO_CATALOG=true`. Для другого порта измените также порт в `ALLOWED_ORIGINS`. Для серверного размещения настройте внешний HTTPS-прокси, публичный адрес в `ALLOWED_ORIGINS`, `COOKIE_SECURE=true` и `SEED_DEMO_CATALOG=false`; `APP_BIND=0.0.0.0` открывает сайт по сети. UUID и SHA-256 в браузере требуют HTTPS либо localhost, поэтому сетевой HTTP не заменяет серверное размещение. Перезапустите сборку после изменения параметров. Отключение начального каталога не удаляет уже созданные товары.

`APP_MODE=api` — рабочий режим по умолчанию. `APP_MODE=demo` выбирает прежний браузерный демонстрационный источник при сборке; его данные остаются в конкретном браузере и не попадают в серверные тома. После изменения режима запускайте скрипт без `--no-build`.

Перенос из исходников: скопируйте проект на новое устройство и запустите `./scripts/start.sh`. Не нужны `node_modules`, `dist`, старые `.env` и Python на принимающем устройстве. Docker соберёт образы для его архитектуры; для ARM используйте этот способ.

Для запуска готовых образов перенесите `artifacts/docker/lavr-crm-full-stack-amd64.tar`, `compose.yaml` и `scripts/start.sh`, сохраняя каталог `scripts`. На устройстве AMD64 с Docker выполните из каталога с Compose:

```sh
docker load -i lavr-crm-full-stack-amd64.tar
sh scripts/start.sh --no-build
```

Архив включает frontend, backend и PostgreSQL. `--no-build` не собирает и не скачивает образы; новая `.env.docker` создаётся из загруженного backend-образа. Исходники `backend/` для этого запуска не нужны. Архив AMD64 не превращается в ARM64; на ARM нужна сборка из исходников. Новый сервер получает новую базу; существующие данные переносятся отдельно с резервной копией и прежними секретами.

Для согласованной резервной копии временно остановите frontend и backend, оставив PostgreSQL работающим:

```sh
umask 077
mkdir -p backups
docker compose --env-file .env.docker stop frontend backend
docker compose --env-file .env.docker exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > backups/postgres.dump
docker compose --env-file .env.docker run --rm --no-deps --entrypoint tar backend -C /data/media -czf - . > backups/media.tar.gz
docker compose --env-file .env.docker start backend frontend
```

Сохраните оба файла и `.env.docker` в защищённом хранилище. Копия содержит контакты заказов и приватные изображения; Docker-архив их не заменяет. Восстановление БД выполняется через `pg_restore`, файлы возвращаются в `media_data` с владельцем UID 1000 перед запуском backend.

## Работа через API

Главная, категории, товары и заказы загружаются асинхронно. Поиск, фильтры, сортировка и пагинация передаются серверу. Ответы HTTP проверяются перед использованием. Форма сотрудника получает сессию и роль с сервера; `manager` работает с заказами, `admin` дополнительно открывает каталог и редактор сайта. Закрытые изменения передают CSRF-токен, изменения существующих заказов, категории товара, настроек сайта и публикаций — `If-Match`.

Адаптер конкретной 1С ещё не подключён. API отвечает `503` на оформление, если не может подтвердить актуальную цену и остаток в 1С; он сохраняет форму и корзину, не создавая успешный заказ из начального каталога. Менеджерские переходы статусов также требуют подтверждённого обмена. Backend-тесты проверяют успешные транзакции с тестовым адаптером; Docker-сценарий проверяет отказ при отсутствии реальной интеграции.

В `localStorage` frontend записывает только черновик корзины `[{ productId, quantity }]` под ключом `lavr.cart.v1`. В `sessionStorage` хранится технический ключ попытки оформления `lavr.checkout-attempt.v1`: UUID и SHA-256 отпечаток запроса, без тела заказа и контактов. Он позволяет повторить запрос с тем же ключом после обновления страницы и повторного ввода формы. Контактная форма, загруженные данные и сессия находятся в памяти страницы. Цена и итог в корзине предварительные; окончательную цену и допустимость заказа обязан проверить backend. При ошибке оформления форма и корзина сохраняются, успех отображается только после проверенного ответа API.

В каталоге администратора подключены создание категории и назначение категории существующему товару. Создание учётной номенклатуры доступно только в демо до согласования записи в неизвестную конфигурацию 1С.

В [CRM → Контент сайта](http://127.0.0.1:5173/#crm-content) администратору доступны три вкладки:

- «Главная и меню»: тексты и изображение первого экрана, кнопка и внутренняя цель, контакты магазина, заголовки разделов, подписи, порядок и видимость пунктов меню.
- «Публикации»: акции, объявления и горячие предложения, текст, до восьми изображений, внутренняя ссылка, порядок, статусы «Черновик»/«Опубликовано»/«В архиве» и необязательный период показа. Даты вводятся по часовому поясу устройства; черновики, архив и записи вне срока не показываются на витрине.
- «Изображения»: загрузка JPG/PNG/WebP до 5 МиБ и 4096×4096 с альтернативным текстом, библиотека с пагинацией. HTTP-клиент отправляет поля `file` и `alt` через multipart; настройки и публикации сохраняют ID медиа, а пути предпросмотра и публичных файлов возвращает API.

Редактор сохраняет существующий дизайн лендинга и обычный текст без HTML. При ошибке изменения остаются в форме; конфликт `412` требует загрузить актуальную версию, уход с несохранёнными изменениями запрашивает подтверждение. FastAPI проверяет роль, Origin и CSRF, версии и содержимое изменений. Изображение доступно публично только при актуальной ссылке с витрины, опубликованного материала или видимого товара; черновики и архив остаются закрытыми. Конструктор страниц и расчёт скидок не входят в редактор.

## Мобильное отображение

Витрина и CRM используют те же Vue-компоненты и API на телефоне, планшете и компьютере. Отдельная мобильная база или backend не нужны. Меню, категории и публикации по-прежнему приходят с сервера; адаптация меняет только отображение.

До 1100 px пункты меню доступны через раскрываемое «Меню», до 760 px поиск переносится на отдельную строку, фильтры — над товарами, корзина и формы — в одну колонку. Основные кнопки и области нажатия на телефоне имеют размер от 44 px; поля ввода и select — шрифт 16 px. Масштабирование страницы разрешено. Таблицы CRM прокручиваются внутри подписанной области, с подсказкой для узкого экрана; остальная страница не требует горизонтальной прокрутки. Кнопка закрытия карточки остаётся доступна при прокрутке диалога.

Приёмка включает мобильные касания на 320×740, 390×844 и 844×390, поиск по артикулу → корзина → заказ, работу с категориями, серверное меню и вход сотрудника. Эмуляция Chrome не заменяет проверку клавиатуры и масштабирования на настоящих iPhone/Android.

## Что проверить в демо

1. Найдите `W 914/2`, `Bosch фильтр` или `BKR6E-11`; попробуйте категорию, бренд, наличие и сортировку цены.
2. Добавьте товар, перейдите в корзину, измените количество. Больше демонстрационного остатка добавить нельзя.
3. Введите вымышленные имя и телефон, например `Демо Покупатель`, `+7 (999) 123-45-67`. Для доставки укажите тестовый адрес.
4. Нажмите «Создать демозаказ». Контакты и состав появятся в CRM текущей вкладки.
5. Откройте карточку заказа и последовательно измените статус: новый → подтверждён → готов к выдаче → завершён. Отмена возможна до завершения; финальные статусы не меняются.
6. Вернитесь в каталог и оформите второй демозаказ. Заказы текущей вкладки сохраняются при обновлении страницы.

В [CRM → Каталог](http://127.0.0.1:5173/#crm-catalog) создайте категорию, затем добавьте номенклатуру: название, артикул, бренд, категория, цена в рублях и остаток. Название категории уникально; одинаковый артикул одного бренда добавить повторно нельзя. Категорию существующего товара можно изменить в таблице. Новый товар сразу доступен на главной, в поиске и корзине; после обновления страницы он сохраняется. Основной поиск — по артикулу, дополнительно поддержаны название, бренд и внутренний/внешний ID.

Главная начинается с трёх примеров акций и объявлений из `src/data/demo-site.js`. В [CRM → Контент сайта](http://127.0.0.1:5173/#crm-content) измените заголовок и меню, загрузите изображение, создайте черновик, затем опубликуйте или архивируйте его. После сохранения витрина обновляется; проверьте результат и после перезагрузки страницы. Публикация рекламной акции не меняет цену товара или заказа.

## Ограничения демо

Цены, остатки, артикулы, описания и изображения демонстрационные; совместимость запчастей не проверяется. Источники и лицензии фото находятся в [docs/assets.md](docs/assets.md) и доступны через ссылку в футере сайта.

Корзина хранится в `localStorage` с ключом `lavr.cart.v1` (только `productId` и `quantity`). Только в demo-режиме заказы с контактами сохраняются в `sessionStorage`, ключ `lavr.orders.v1`, в текущей вкладке; восстановление вкладки браузером может восстановить и сессию. Используйте вымышленные контакты. Для явного удаления демоданных очистите хранилище этого сайта в настройках браузера.

Категории и номенклатура сохраняются в `localStorage`, ключ `lavr.catalog.v1`, и обновляются между вкладками этого браузера. Ошибка записи не очищает формы и не применяет изменение. Если сохранённый каталог повреждён или недоступен, UI показывает исходный демокаталог и блокирует изменения/оформление, сохраняя прежние данные. После восстановления корректного каталога работа возобновляется. Это локальное демо без совместного редактирования несколькими менеджерами; одновременные записи из вкладок используют последнюю сохранённую версию.

Настройки сайта и публикации сохраняются JSON-снимком в `localStorage` под ключом `lavr.site.v1`; загруженные файлы — как Blob в IndexedDB `lavr-media-v1`. В JSON хранятся ID изображений; временные `blob:`-адреса создаются заново при чтении файлов. Ошибки записи сохраняют форму и прежние данные, повреждённый JSON переводит редактор в режим чтения. Версии записей обнаруживают устаревшее сохранение, но демо не заменяет серверные транзакции или общую медиабиблиотеку. Очистка хранилища сайта удаляет эти изменения и файлы.

Демозаказы не отправляются магазину или в 1С, CRM в демо открыта. Это режим согласования интерфейса с вымышленными данными. В API-режиме работают серверная авторизация, PostgreSQL, общий каталог, заказы и медиабиблиотека. Реальный обмен с 1С ещё предстоит: неизвестна конфигурация и доступ к базе заказчика.

Для рабочей CRM и витрины MVP подтверждён Vue 3 + Vite. SEO отложено до следующих этапов; необходимость Nuxt будет оцениваться после MVP.

## Архитектура и дизайн

Публичная витрина и административная зона используют общий интерфейс источника данных: `src/data/http-api.js` для API и `src/data/demo-api.js` для явного демо. Реализованный FastAPI проверяет права и изменения; PostgreSQL хранит данные, постоянный media volume — файлы. Сессии сотрудников хранятся на сервере, браузер получает HttpOnly cookie; аудит фиксирует изменения. Цены и остатки заказа проверяются сервером, повторный запрос с тем же ключом не создаёт второй заказ.

## Проверки

```sh
npm test
npm run check
npm run build
npm run build:demo
```

Тесты используют встроенный `node:test`: домен демо, источники данных, проверка HTTP-ответов, схемы контента и медиа, сохранение публикаций и версий, черновик корзины и действия со статусами. Сборки проверяют компиляцию Vue templates и выбор источника.

Для интеграционной проверки Docker нужны оба собранных образа и Node.js на машине проверки:

```sh
APP_MODE=demo docker compose --env-file .env.docker build frontend
APP_MODE=api docker compose --env-file .env.docker build frontend
node --test tests/docker-smoke.mjs
```

Сценарии запускают временные контейнеры и HTTP-сервер проверки, затем удаляют их. Проверяются выбор источника, пользователь без root, healthcheck, HTML/assets и 404, передача API-пути/заголовков/cookie, multipart 5 МиБ и отказ для тела больше лимита Nginx. Проверка proxy использует HTTP-сервер теста, а не реализованный FastAPI.

Дополнительная браузерная проверка требует установленный Google Chrome и временный Playwright. На macOS/Linux его можно установить вне проекта:

```sh
npm install --prefix /tmp/lavr-browser-qa playwright
```

Демо-сценарии `tests/browser-smoke.mjs` ожидают `http://127.0.0.1:5173`. Запустите `npm run dev:demo` либо соберите демо и в отдельном терминале откройте preview на этом порту:

```sh
npm run build:demo
npm run preview -- --port 5173 --strictPort
```

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/browser-smoke.mjs
```

Скрипт проверяет заказ, каталог, редактор контента, сохранение загруженных файлов после перезагрузки, обмен вкладок, ошибки хранилища, клавиатуру, мобильные касания и размеры элементов; перезаписывает скриншоты в `docs/previews` тестовыми данными.

`tests/browser-api.mjs` проверяет production API-сборку с перехваченными HTTP-ответами. Перед ним соберите `npm run build` и запустите preview на том же порту 5173:

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/browser-api.mjs
```

Это проверка клиента на HTTP-заглушке. Реальный FastAPI/PostgreSQL проверяются отдельно backend-тестами и сквозным сценарием полной Docker-сборки.

Для backend-тестов нужен Python 3.13 и отдельная тестовая PostgreSQL с именем базы, заканчивающимся на `_test`. Задайте `TEST_DATABASE_URL` для неё; каждый тест создаёт и удаляет изолированную схему, рабочую БД указывать нельзя.

```sh
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
cd ..
```

После `./scripts/start.sh` сквозной сценарий проверяет настоящий Nginx, FastAPI, PostgreSQL и изображения на компьютере и мобильном экране, без перехвата HTTP-ответов:

```sh
PLAYWRIGHT_MODULE=/tmp/lavr-browser-qa/node_modules/playwright/index.mjs node --test tests/full-stack.mjs
```

Он читает пароль администратора из локальной `.env.docker`, создаёт служебные материалы, возвращает исходный баннер и оформление товара, архивирует проверочную публикацию и скрывает проверочную категорию. Проверка выполняется на тестовой установке; запись аудита и загруженный проверочный файл остаются в её серверных данных. Другой адрес задаётся через `BASE_URL`, другой файл окружения — через `DOCKER_ENV_FILE`.
